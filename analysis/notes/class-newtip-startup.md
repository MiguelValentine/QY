# `com/newtip.fcc` 类声明与启动对象节点

## 范围

本记录只追踪 `CLIENT/index.fcc` 中的 `kind=603` 对象节点，以及 `CLIENT/com/newtip.fcc` 中 `kind=1520` 类声明和后续同名对象节点。依据是本地 `tokens` / `compile` 输出与 `analysis/disassembly/objsys.annotated.asm`。未运行原版客户端，未据此声称观察到游戏启动行为。

## 已确认

- `CLIENT/index.fcc` 的 token 偏移 `0x140` 有 `#include "com/newtip.fcc"`。约 `0x320` 出现 `kind=603`，紧随其后的 `kind=6` 值为 `0xb77e2e86`，随后是 `kind=602` 的 `>`，再后是 `{`（偏移 `0x332`）。这确认启动入口在前面的桌面设置语句之后包含一个以该哈希开头的对象语法节点；token/AST 本身不证明其执行效果。
- `CLIENT/com/newtip.fcc` 偏移 `0x14` 开始 `kind=1520`（class）；类名哈希为 `0xcca02540`，冒号在 `0x20`，基类哈希为 `0xb77e2e86`，块起始 `{` 在 `0x2c`。其块关闭后有 `obj` 声明 `Form`（`0x2a8`），随后 `Form = new <0xfb3f066f>`（`0x2c0–0x2d8`）。
- 同一 FCC 后部偏移 `0x7c4` 有 `kind=603`，其后类名哈希是 `0xcca02540`，然后是 `kind=602`（`>`）；这与编译 AST 中 `form: "object"`、token offset `1988`（十进制，即 `0x7c4`）相符。该 token 之后有块结束标记，具体节点边界按 parser AST 结构，而非把后续文件内容都视作该节点。
- 原生 `0x1000ffa0` 是按标记 kind 分派的处理路径之一。其前段在 `0x10010135–0x1001013c` 通过表项间接分派；kind `603`（`0x25b`）由比较分支 `0x100107bf–0x100107c4` 送到 `0x1001081b`。该分支会读取后续 token，并在语法不符合时产生“需要类名”等解析错误文本。此处证明了原生 parser 对 kind `603` 有专门语法处理，不单独证明该节点会创建游戏对象。
- kind `1520` 的处理位于 `0x100112f6` 起：原生代码校验类名、要求 `:` 并读取基类名（`0x100112f6–0x10011336`），分配 8 字节结构（`0x10011337`），分别经 FBase #788 计算两个名称值（`0x1001137b`、`0x10011389`），再调用 `0x1000a050`（`0x10011394`）。调用成功后经 `0x10011f10` 写入解析对象字段，并调用 FBase #799（`0x100113c7–0x100113d9`）。
- `0x1000a050` 的函数体先处理旧的引用计数记录，再分配 16 字节记录并写入传入字段（`0x1000a070–0x1000a0c9`）；接着初始化 parser 节点并调用 `0x1000f650`，其后在特定分支建立另一份 12 字节记录并调用 `0x1000ffa0`（`0x1000a0d2–0x1000a16f`）。因此它不宜简化描述为“只分配 8 字节 class 记录”；在当前反汇编证据中也没有看到它直接调用游戏窗口/游戏对象构造器。
- class 分支在 `0x100113c7–0x100113d9` 先 `push 0`、以 `ECX=EDI` 调 `0x10011f10`，再以 `ECX=EBP`、参数 `(ESI, 4)` 调 FBase #799。该 parser 路径上的 `EDI` 来自 `0x10010064`：将此前分配的对象传给 `0x10011ec0` 并以其返回值覆盖 `EDI`。`0x10011f10` 的函数体明确把参数写入 `ECX+4` 并递增全局 `0x100ca248[index]`，所以此处写入的是该解析节点 `EDI+4=0`；随后 #799 接收的 `ESI` 与立即数 `4` 是另一组参数。
- 在 parser 构造该节点时，`0x1001006a` 从局部变量取待输出容器作为 `ECX`，以 `EDI` 和 `0` 调 FBase #513（`0x1001006a–0x10010083`）；紧接着 `EBP=EDI+8`（`0x10010083`）。因此 class 分支调用 #799 时 `ECX=EBP` 正是节点 `EDI+8` 的 payload 容器，#799 将 `ESI` 以 tag `4` 放入该节点 payload；这与前一步写入 `EDI+4=0` 是两个不同字段。
- `0x10065fa0` 用第一个栈参数经 FBase #525/#520 取得同一语句对象到 `EDI`，读取对象 `+4` 作为跳表索引，并设置 `ESI=EDI+8`（`0x10065fbe–0x10066045`）。所以 class 节点的 `+4=0` 会进入 index 0 分支，而其中 FBase #782 从 `ESI` payload 取出 tag 4 对应的 class 值，再交给 `0x1000a460` 缓存路径。这里 tag 4 是 payload 元素标签，执行器 opcode 是节点 `+4` 的 0；两者不应混为一谈。
- 执行器 index 0 的分支（`0x1006604c–0x1006609c`）先用 `EDI+8` 调 FBase #782 取得值；此处 `EDI` 是由执行器首个栈参数经 FBase #525/#520 返回的语句对象。若值非空，就从执行上下文 `+0xb8` 取得/创建缓存对象，并调用 `0x1000a460`。后者读取传入值对象 `+4` 的引用对象及其 `+4` 负载，交给 `0x1000a230`；成功后将原值交给 `0x1000a1e0`。这条路径按类名和 `(0, 1)` 查找或建立缓存条目，并复制相关引用；case 0 本身不遍历/执行类体。class parser 的 #799(tag 4) 写入的 payload 与执行器从同一语句节点 `+8` 读取的 payload 在静态数据流上闭合。
- 新增的符号查询结果：`go run ./analysis/tools/symbol_lookup 0xb77e2e86 CLIENT/objsys.dll CLIENT/fbase.dll` 在 `objsys.dll` 文件偏移 `669452` 找到字符串候选 `"wnd"`。哈希 `0x96712ccc` 在 `objsys.dll` 文件偏移 `664060` 找到 `"size"`。这是 DLL 字符串/哈希匹配候选，不是对脚本符号绑定或结构字段语义的单独证明。
- `0x1005d7e5` 将常量 `0xb77e2e86` 写到基对象结构的 `+0x0c`。结合符号查询，`"wnd"` 是该值可能对应的名称候选；仍需记录具体调用点传入/比较的实际值，才能确认它是窗口类名、字段名还是其他哈希。当前对反汇编文本中该字面量的检索仍只命中此处；这不足以证明它就是类注册 ID。
- `0x10065fa0` 对象 `+4` 的分派值大于 `0x14` 时转到 `0x10067b23`，否则查表 `0x10067bf0`。对 class 节点已闭合的映射为节点 `+4=0` 进入 index 0，而其 `+8` payload 中的 class 值以 tag 4 标记；不能把 payload tag 当成语句 opcode。

## 推断

- `0xb77e2e86` 很可能是由脚本使用的窗口/基础对象类型关联哈希；`"wnd"` 是现有 `objsys.dll` 字符串池找到的候选名称。它同时出现在 `index.fcc` 对象头、`com/newtip.fcc` class 基类位置，以及一个原生对象初始化结构字段中，但这些共现还不能决定该 hash 在各处是否都指同一语义。
- class parser 将 opcode `0` 写入语句节点 `+4`，并以 tag `4` 将 class 值写入同一节点 `+8` payload；执行器 index 0 消费该值并建立缓存条目。类体是否在类登记时立即执行，仍不能单由 case 0 判断；对象创建分支另行处理类体的递归执行，见 `analysis/notes/object-node-kind603.md`。

## 未知与边界

- FBase #788、#799 和 `0x1000a050` 的精确高层语义尚未完全恢复；现有调用关系只支持上述数据流描述。
- #799 对象 tag `4` 与语句 opcode `+4` 是不同层次的字段；已确认 class payload 经执行器 case 0 消费，但类体的逐语句语义仍须结合对象创建 opcode `0x0a` 的调用链判断。
- 未证明 `0x1000a050` 是游戏对象构造函数或完整类注册函数，也未证明 `0x1005d7e5` 的 `+0x0c` 字段在所有上下文中都是脚本类标识。
- parser 对入口对象块先构造 opcode `0x0a` 节点；对象工厂和可选初始化块执行发生在该节点进入 `0x10065fa0` 执行分支之后。静态路径已确认二者分阶段，但未观察原版运行时是否成功走到该对象节点。
- 负向检索边界：仅在现有 `analysis/disassembly/objsys.annotated.asm` 文本中搜索 `0xb77e2e86`、其十进制值 `3078499974` 与相关类名哈希；这不是对所有 DLL、未注释数据段或运行态内存的穷尽证明。
- 本记录没有修改 Go 运行时或桌面程序；它不表示当前实现已达到“可以进入游戏”。
