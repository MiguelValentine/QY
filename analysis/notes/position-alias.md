# `pos` 属性与坐标别名调查

## 结论

`wnd` 明确注册了 `pos` getter 和 setter。setter 将输入解析为至少两个值，并把索引 `0`、`1` 的分量交给窗口对象的位置虚拟接口；getter 从同一接口取回两个分量，并按索引 `0`、`1` 返回。它与 `xpos`、`ypos` 共享位置虚拟接口，因此可确认 `pos` 是一对坐标分量，而非普通字符串别名或 `posex`。

`SYSTEM.FCC` 的 `ToolTips.tptext:text` 写入 `pos=8,2`，所以该实例请求的位置分量为 `(8,2)`。`wnd` 构造器把包含矩形/位置字段的存储区域清零，默认位置为 `(0,0)`。这些是静态二进制与资源证据，不代表已观察到原版运行时的最终屏幕坐标效果。

## 登记与实现

- 名称 `pos` 位于 `objsys.dll` VA `0x100a221c`，文件偏移 `0xa221c`。原始字节可见 `CLIENT/objsys.dll` 偏移 `663812` 的字符串表片段。
- `objsys.annotated.asm:0x1004f0d1–0x1004f0dd` 以 getter `0x1004d960` 登记 `pos`；`0x1004f0e2–0x1004f0ee` 以 setter `0x1004e0e0` 登记同名写访问器。
- getter `0x1004d960` 先用 FBase #789 检查目标值容器，再调用窗口对象 vtable `+0x68`（此对象的槽目标为 `0x1005c620`）写出两个值，随后经 FBase #785/#748 将它们作为索引 `0`、`1` 写入返回值。`0x1005c620` 明确依次读取对象 `+0x14` 和 `+0x18`。
- setter `0x1004e0e0` 调 FBase #768 解析输入，要求返回的分量数至少为 `2`；不足时返回失败。成功时取出两个解析值，调用对象 vtable `+0x64`（此对象的槽目标为 `0x1005c550`）写入。`0x1005c550` 按顺序把两值写入对象 `+0x14` 和 `+0x18`。该回调没有 `pos` 专属字符串/文本处理。
- `xpos` getter/setter（`0x1004d9f0`、`0x1004e040`）和 `ypos` getter/setter（`0x1004da20`、`0x1004e090`）也通过同一对 vtable `+0x68`/`+0x64` 位置接口读取或更新单个分量。因此 `pos` 与这两个单轴属性针对同一位置状态。
- `wnd` 构造器 `0x1005d720` 在 `0x1005d792–0x1005d79c` 从对象 `+0x14` 起连续清零 `0x69` 字节，故 `pos` getter 直接读取的 `+0x14`、`+0x18` 初值均为零。独立的 `rect` 访问器 `0x1004daa0` 将 `+0x24`、`+0x28`、`+0x2c`、`+0x30` 作为四个矩形分量读取；这些矩形槽位也在清零范围内。

## 脚本实例与边界

`SYSTEM.FCC` 的 `ToolTips.tptext:text` 先写入 `pos=8,2`，再创建 `tptext` 实例；资源详情见 [tooltips-resource.md](tooltips-resource.md)。这证明该脚本按二分量位置接口赋值。对 `pos` 的哈希 `0x6a953fb0` 搜索没有找到结果，原因是这里按字符串地址 `0x100a221c` 登记，而非在该访问器路径中比较这个哈希值。

静态反汇编足以闭合属性登记、分量数量、传递顺序以及默认清零状态；最终坐标是否受父窗口偏移、缩放、裁剪或后续脚本改写影响，仍需追踪对应 vtable 实现与运行时绘制路径。字符串 `"pos set error!"` 位于 `0x1002ea0b` 一带的 MCI 音频 seek/播放错误路径，不是本属性的错误或坐标证据。
