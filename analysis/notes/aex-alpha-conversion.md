# AEX 透明度平面转换

## 静态路径

依据为 `analysis/disassembly/fbase.annotated.asm` 和原始
`CLIENT/fbase.dll`；没有运行原版 Windows 客户端。

FBase `#69` 在 `0x10029912–0x10029921` 用 `#448` 加载第二平面，
再于 `0x1002995b` 调用 `#439(1)`，将图像改为单字节灰度格式。
`#448` 先进入 `0x10022ed0`。该函数在 `0x10022eff` 比较的六字节
常量 `0x10058178` 实际为 `GIF89a`，匹配后走 GIF 解析
`#256`，不是 OLE 回退。

`0x10022f64–0x10022f71` 用全局 `#423` 创建图像；
`#423` 的 RVA 为 `0x6385c`，原始 DWORD 值为4。
`#260`（`0x1002e710`）将 GIF 调色板的 RGB 值交给
`#387`（`0x1001a9c0`）并以两字节写入图像。格式4为 RGB565，
不是32位格式。JPEG 路径先创建格式5的三字节图像，再调用
虚表 `+0x10`，即 `#439`，转换为相同的默认格式4。

`#439` 的对象虚表 `0x10057680` 前五项为：
`0x10004ad0`、`0x10023380`、`0x10023240`、`0x100231f0`、
`0x10024350`。其中 `+4` 调用 `#436` 重建图像，
`+0xc` 清空图像字段。重建成功后，`#439` 将保存的旧图像描述
传入 `#344`，复制并转换像素。透明度平面请求格式1，
因此不是已经为格式4时的相同格式早退。

`#344` 的格式4输入分支 `0x1001e000–0x1001e03b` 还原补零的
RGB565 通道后调用 `#428`。其格式1分支
`0x1001ab8e–0x1001abb7` 计算三通道整数平均：

```text
gray = ((R & 248) + (G & 252) + (B & 248)) / 3
```

所以灰度输入也会先损失 RGB565 的低位，不能直接使用输入的红通道。
该转换不涉及最终绘制时的 alpha 混色。

在已保存的 FBase 和 objsys 反汇编引用范围内，`#423` 只有读取，
未发现写入。Go 当前采用原始默认值4；不声称覆盖外部修改该全局值
后的行为、其他 GIF 加载分支或 Windows 图像解码器逐像素差异。

## 函数仿真

`analysis/tools/oracle_aex_gray.py` 用 Unicorn 直接执行原始 DLL：

- `#428` 覆盖全部通道和 `0..765`、全部灰度值及额外偏色样本，
  共1026次调用，均与整数平均一致。
- `#344` 以格式4输入、格式1输出执行完整转换，输入全部65536个
  RGB565 值，均与通道补零后整数平均一致。源、目标描述及裁剪矩形
  在仿真器中显式构造，没有替换转换函数或挂钩其内部算术。

证据保存在 `analysis/evidence/aex-gray-oracle.json`，含 DLL 哈希、
函数地址、仿真器版本和输出哈希。该仿真不运行 DLL 初始化、GIF
解析或整个原版客户端。

## 真实资源

`in/img/map/root/land_04.ale` 的第二平面为566×254的单帧 GIF。
16个调色板索引均被使用；唯一非灰条目为索引10，
RGB `(145,145,144)`，共891个像素。默认路径先量化为
`(144,144,144)`，最终透明度144。这排除了“只跳过未用的非灰
调色板项”的处理办法。

修正后真实 Go 入口越过该资源及后续地图构造，最初在
`index.fcc:0x2924` 创建 `btn_index` 后的 `OnCreate` 少参数检查
处停止。后续已按原生签名查找修正事件分派，并越过此处，
见 [事件签名分派](event-signature-dispatch.md)。
这些结果只证明启动执行推进，不代表已经绘制地图或进入游戏。
