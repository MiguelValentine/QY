# `bk := null` 静态执行路径

## 范围与证据

本笔记核对 `CLIENT/index.fcc` 中的 `bk := null`，重点区分脚本绑定处理、`bk` 背景对象内部状态及其资源释放。证据来自 `CLIENT/index.fcc` 的离线 token 转储和 `analysis/disassembly/objsys.annotated.asm`。未运行原版客户端；静态控制流不代表观察到运行时画面变化。

## token 与编译分支

- `go run . -client CLIENT tokens index.fcc` 显示文件偏移 `0x15e` 的 token 为 kind `1523`、文本 `null`。目标语句在更早的 token 中包含 `bk` 哈希 `0x4d18dd80` 和 kind `1212`（`:='）；相关 FC0A token 语义见 [`binding-assignment.md`](binding-assignment.md)。
- `objsys!0x100101a9` 将 kind `1212` 送到编译分支 `0x10010428`。该分支先构造绑定目标节点；随后在 `0x10010521–0x10010553` 检查绑定运算符并读取 RHS。
- RHS 为 kind `0x5f3`（1523）时，`0x10010572` 命中专门分支。`0x1001057a–0x1001057e` 把执行节点 `+4` 设为 `5`，再于 `0x10010583–0x10010590` 前移 token 并返回编译主循环。因此这条 `null` 形式编译为 opcode `5`，不是 [`binding-assignment.md`](binding-assignment.md) 中 `bk := color(...)` 使用的 opcode `0x0e` 调用形式；此处也没有把 `null` 改写成 `bk` 的 `color` selector。

## opcode `5` 执行路径

- 执行器 `0x10065fa0` 从节点 `+4` 取 opcode，经跳表 `0x10067bf0` 分派。该表索引 `5` 的槽位位于 `0x10067c04`，内容为 `0x10066801`。
- `0x10066801` 以 FBase `#803` 校验 payload 形状，再以 FBase `#785` 取前两项并经 `#788` 取得两个 DWORD 值，传给 `0x10065820`；传入的接收对象是执行上下文 `-0x14(%ebp)`。helper `0x10065820` 检查该对象 `+0x9c` 容器中的记录，按记录 `+0x0c`、`+0x10` 匹配两个 DWORD。匹配时只把记录 `+0x1c` 置为 `1` 并返回 AL=`1`；未匹配时返回 AL=`0`（`0x10065823–0x10065881`）。
- 该返回值用于 `0x1006684d–0x10066852` 的控制流分支，不能视作被忽略：`AL=1` 跳到 `0x1006689c`；`AL=0` 时检查 handler 参数 `[ebp+8]`，参数为零则直接回到 `0x100660b9` 主循环，非零则在 `0x1006685c–0x10066897` 构造诊断后同样回主循环。未命中时 helper 返回 `AL=0`，这条路径没有创建记录。opcode `5` 的可见路径没有调用 `bk` 的 vtable 分派器 `0x100435f0`，也没有调用其清理函数 `0x100435d0`。helper 的直接写操作是记录标志，不是记录删除或资源释放。
- 同一 `+0x9c` 记录表的另一路径 `0x10065750` 也按 `+0x0c/+0x10` 两键查找；缺项时经 `0x1005f110` 查询全局工厂表 `0x10121e6c`，调用匹配的工厂创建记录，并把传入的 selector 写入返回记录 `+0x0c`（`0x1005f110–0x1005f14b`），随后调用记录 vtable 首槽。全局工厂表确有 `bk` 项，对应工厂 `0x10045f40`，见 [`system-background-color.md`](system-background-color.md)。这说明该通用记录机制可按 selector 创建 `bk` 相关记录；但现有证据不能证明此处传入的 selector 就是 `bk`，也不能证明 opcode `5` 的 payload 一定命中该项。该路径按虚调用 AL 将记录 `+0x1c` 置 `0` 或 `1`（`0x10065750–0x1006580e`）。
- 已找到 `+0x1c` 的后续消费者：宿主更新函数 `0x1005daa0` 遍历 `+0x9c` 记录表；若当前记录 `+0x1c` 非零，则调用记录 vtable `+0x14`，否则检查 `record+0x14`，仅在其非零时调用 vtable `+0x08`，然后继续遍历（`0x1005dae0–0x1005db1c`）。`TableDesk Update` 的调用点 `0x10076a50` 明确调用该更新函数；反汇编中另有多个调用点，因此该消费者并非仅限于此调用者。结合置位路径，可确认 `+0x1c=1` 会在宿主更新时选择 vtable `+0x14` 回调；但静态证据尚不能确定该槽的高层语义，或该回调是否解绑、销毁对象或改变背景绘制状态。
- 对 `bk` vtable 的该槽已可直接闭合：`0x1004358c` 将对象 vtable 设为 `0x100a1b58`；原始 `.rdata` 中 `0x100a1b6c`（vtable `+0x14`）的小端 DWORD 为 `b0 5d 04 10`，即直接目标 `0x10045db0`。此函数检查 `bk+4` 宿主指针；非零时将 `bk` 作为参数调用 `0x1005bfa0`，该 helper 通过 FBase `#515` 从宿主 `+0x9c` 容器移除该对象，并在对象 `+0x18` 非零时设置宿主 `+0x48` 的 `0x20` 位（`0x1005bfa0–0x1005bfc2`）。随后 `0x10045db0` 递减全局对象计数、清零 `bk+4`、将对象从全局双向链表摘除并将链表节点放回空闲链表，最后尾调用其 vtable `+0x0c`，即 `0x100435d0`。析构函数检查并释放 `bk+0x24`，再将该字段清零（`0x100435d0–0x100435eb`）。因此，对确由该 `bk` vtable 执行的 `+0x14` 回调，可确认它会脱离宿主记录容器并运行对象析构，且会释放 `+0x24` 所持资源；该路径没有清零背景颜色字段 `+0xc4`，也没有显示释放 `bk` 对象本身的分配块。
- `0x1005d9a6` 是不同的宿主清理路径：它遍历并从 `+0x9c` 容器移除记录、清零记录 `+4`、递减全局计数，再无条件调用每条记录 vtable `+0x14`（`0x1005d9a6–0x1005d9d9`）。因此不能把更新函数中受 `+0x1c` 控制的分支与宿主清理时的无条件回调混为一谈；也不能仅凭两处调用槽位相同，断定它们具有完全相同的高层效果。
- `0x10065820` 也由 `0x10068f6d` 的空间距离扫描代码调用；该调用以常量 `0x297b15c8` 和 `0` 查询同一记录。这说明 helper 本身是对 `+0x9c` 记录的通用匹配/标记操作，不能单凭其名字或返回值将其解释为“清背景”。
- `0x1006689c` 仍属于 opcode `5`：它检查 `[ebp+8]`，参数为零时回到 `0x100660b9` 主循环；非零时格式化诊断，并在 `0x100668df` 无条件跳回主循环。这里没有递归执行。`0x100668e4` 已开始下一个 opcode handler，不属于 opcode `5`。opcode `5` 的这些路径没有显示对 `bk` 背景字段 `+0xc4` 的直接写入。

## 背景对象与边界

`bk` 对象的初始化/清理分派器 `0x100435f0` 在处理 selector 前会释放并清零对象 `+0x24`，随后按哈希分派；析构路径 `0x100435d0` 也会释放并清零 `+0x24`。`color` selector 则把 RGB565 状态写入对象 `+0xc4`，见 [`system-background-color.md`](system-background-color.md)。这些是背景对象自身路径的证据，不证明 `bk := null` 会到达它们。

**可确认：** `bk := null` 进入 opcode `5`；可见 opcode 路径在执行上下文的 `+0x9c` 记录中按两个值查找，命中时设置记录 `+0x1c=1`。对具有 `bk` vtable `0x100a1b58` 的命中对象，后续更新选中槽 `+0x14` 会将其从宿主 `+0x9c` 容器及全局链表脱离、清除宿主指针、运行 `0x100435d0` 析构，并释放字段 `+0x24` 持有的资源。已观察到的这条析构路径不清零背景像素字段 `+0xc4`。

**尚未知：** opcode `5` 的两项键在高层语义上对应什么对象/变量，以及本脚本的这两个键是否确实命中该 `bk` 实例；虽然该实例的 `+0x14` 回调和析构路径已闭合，但仍未追到此处释放字段 `+0x24` 具体代表哪类资源、引用计数如何影响其最终释放，也未证明 `+0xc4` 会由更晚的绘制/更新路径清空或停止使用。静态证据支持“解除宿主绑定并运行对象析构、释放其 `+0x24` 引用资源”，但不支持“清除背景颜色状态”或“释放 bk 对象分配块”的结论。

## 实现提示

Go 当前的 `Background.NullBound` 模型设置空绑定标记并保留既有 `Kind`、`Color`、`Image` 等字段；这是保守的移植模型，不是对原版绘制结果的结论。不要把 `bk := null` 直接等价为 `Background.Clear()`。原生 `bk` 的延后回调确实脱离宿主容器并运行析构，且析构释放 `+0x24`，但目前未见它清零 `+0xc4`；脚本键到具体 `bk` 实例的对应仍需成立，且对象分配块是否另行释放尚无证据。因此应将解除绑定、背景状态、绘制效果、资源引用释放和对象内存回收分别建模。
