# 对象删除生命周期

## 入口与分派

- `objsys.dll!0x1005a170–0x1005a17a` 将脚本方法 `DelThis` 登记到 `0x10057a90`；小写 `delthis` 也登记到同一函数。
- `0x10057a90` 从调用参数取对象，读取对象首 DWORD 的 vtable，并调用槽 `+0x60`，之后返回整数 0。该入口本身不直接释放对象。
- `Wnd` 构造器 `0x1005d720` 在 `0x1005d745` 写入 vtable `0x100a3270`。`CLIENT/objsys.dll` 的 `.rdata` 在 `0x100a3270` 起给出槽表；槽 `+0x60`（第 25 项，字节偏移 0x60）的目标为 `0x1005c4d0`。

## Wnd 删除标记与子对象

`0x1005c4d0` 是 Wnd 的槽 `+0x60` 实现：

- 检查对象 `+0x08` 的低位。若 bit 0 已置位则直接返回，具备重复调用保护。
- 若 `+0x08` 的 `0x10000` 位已置位，会记录 `ptr err!` 并返回；这说明该对象状态不适合再走该删除入口，具体状态含义尚未完全恢复。
- 否则将 `+0x08` 的 bit 0 置位并清除 bit 1，同时在 `+0x48` 设置 `0x40`。
- 随后遍历对象位于 `+0x94` 的子对象集合，对每个子对象读取其 vtable 并调用同一 `+0x60` 槽。因此 Wnd 删除标记会递归传播到其登记的子对象；重复标记由每个对象自己的 bit 0 检查拦截。
- 若对象 `+0x08` 的 `0x200` 位已置位，标记后还会调用 `0x1005ab90`，参数包含事件哈希 `0xea796c20`；这是删除过程的额外事件分支，但静态证据不足以确认该哈希的可读名称及回调时序效果。

## 延迟清理

- 父对象更新入口为 `0x1005daa0`。它先处理 `+0x9c` 上的绑定，再从 `+0x94` 子对象集合取对象。
- 子循环 `0x1005db2e–0x1005db9a` 检查子对象 `+0x08` 的 bit 0。未置位时调用子对象 vtable `+0x0c`；已置位时调用 vtable `+0x04`，再记录 `Del sub Obj`，并在 `0x1005db6e–0x1005db74` 调 FBase `#517` 从父对象 `+0x94` 集合移除该子对象。
- 对 Wnd vtable，槽 `+0x04` 是 `0x10040350`。该 thunk 对非空对象调用其 vtable 首槽并传入 `1`。Wnd 析构入口 `0x1005e230` 的代码从 `0x1005e263` 起执行清理，因此已标记的子对象会在父对象更新遍历中进入其清理/析构路径，然后从父子集合摘除。
- 所以 `DelThis` 的可见语义是“立即标记并递归标记子对象，稍后由父对象更新完成子对象清理和摘链”，不是在脚本调用点同步释放。若删除发生在父对象已经遍历完子集合之后，最早只能由后续一次父更新处理；若发生在绑定阶段、子循环开始前，则该次更新的后续子循环有机会处理。具体帧内时点取决于调用来源。

## Go 实现建议与边界

- `DelThis` 应把对象转入逻辑失效/待删除状态，并递归标记当前子对象快照；重复删除保持幂等。标记时保留对象仍可被父更新遍历到的关系，避免在回调栈内直接改父子切片。
- 父更新阶段单独 sweep 待删除子对象：调用 Go 侧清理钩子、从父集合摘除，并保证同一轮遍历中的新变更不会跳过相邻对象。子级先标记不等于子级已被物理销毁。
- 当前静态证据确认 Wnd 子对象递归标记及父更新中的延期清理路径；未确认所有非 Wnd vtable `+0x60` 的语义、删除事件 `0xea796c20` 的完整行为、根对象如何删除，以及 FBase `#517` 的内部释放策略。不要据此推断所有对象类型都采用完全相同的递归规则。
