# `files_dir.dz` 启动资源目录分派

## 范围与证据

本文追踪 `CLIENT/com/kele8com.fcc` 在偏移 `0x39e` 的 `pdesktop` 调用及其静态分派，不执行原版程序、不访问网络。主要证据为 `objsys-disassembly.json`（Evidence `ev_79268ca8fa4f56c3fa122adeae94d4774f186500c9d5deb328525b66ac46cbaf`）和 `fbase-disassembly.json`（Evidence `ev_5fc95fa046397bf605b945fbf373993a52efed99a223a6fc52164b61aa8a1e0a`）；反汇编文本位于 `analysis/disassembly/objsys.annotated.asm`、`analysis/disassembly/fbase.annotated.asm`。地址为模块基址 `0x10000000` 下的 VA。

FCC 在 `0x39e` 提交参数 `URL + "files_dir.dz"`，成员哈希为 `0xaf665c57`。`objsys!0x10061b92–0x10061cbe` 按该哈希跳到 `0x10061c82`：先由 FBase #779 检查值类型码是否为 `3`；不是字符串则跳到 `0x10061ecc`，将 native 分派状态设为 `2`。字符串路径经 #808 和 #646 取得字符串指针，传给 `objsys!0x1001a1a0`。返回后该分支不检查被调函数的 `EAX`，清理临时值并走公共出口；公共出口将分派器 `EAX` 置零。参数错误状态、分派状态和脚本表达式值是不同层次，不能据此声称脚本得到某个布尔或成功值。

## `0x1001a1a0` 的可见行为

该函数的入口参数是上述字符串指针（`0x1001a1a0–0x1001a1c7`）。它先调用 FBase #217 检查/处理输入；该步骤返回零时记录一条诊断并跳过后续循环（`0x1001a247–0x1001a268`）。#217 的实现（`fbase!0x10009090`）检查输入中的 `"http://"`，再按扩展名和全局 PathMapping 记录处理字符串；可见分支会组合映射目录与文件名，生成 `.dll` 或 `%08X.fch` 候选路径（`fbase!0x10009158–0x100092c9`）。它没有调用文件打开/读取 API。该行为说明资源路径可经过本地映射和候选名构造，但不能据此断言当前 `files_dir.dz` 已映射成功。

继续路径经 `0x1001a0a0` 处理输入并由 FBase #216 产生可迭代内容，随后通过 #729 计数循环。#216 的已见实现扫描末尾分隔符 `/` 或 `\` 并把字符串拆成两段（`fbase!0x10008b90–0x10008c47`），因此至少有路径/文件名拆分操作；`.dz` 内容格式本身仍未恢复。循环内对条目做字符串/分隔符处理，并构造对象：调用 `0x100185a0`、`0x10018860`，将字段写入新对象，再把对象关联到全局容器 `0x100b6d64`（`0x1001a2bf–0x1001a524`，尤见 `0x1001a4c2–0x1001a506`）。这些是解析和内存状态登记的静态证据；字段所代表的完整业务含义尚未恢复。

函数内部存在输入处理失败或无可迭代条目的分支，并最终统一清理局部对象（`0x1001a526–0x1001a5be`）。对 `0xaf665c57` 分支而言，宿主分派器忽略 `0x1001a1a0` 的返回寄存器，因此调用者没有依据该返回值决定是否继续启动或向脚本提供结果。

## 同步 I/O 与“只排队”判断

在 `0x1001a1a0`、FBase #217 和 #216 的已列出指令及直接调用中，没有看到文件打开/读取、URL 下载、网络连接、等待或完成轮询 API；可见工作主要是字符串拆分/映射、迭代和对象/容器构造。因此**静态证据支持此入口在当前函数内解析路径/条目并登记内存对象，不支持把它描述为已同步下载或读取 `files_dir.dz`**。但这不足以证明整个程序或所有间接 helper 都不会触发 I/O：相关 helper 的完整调用树及新建记录的后续消费者没有在本次范围内闭合。也无法证明这些记录只是异步队列、何时被消费，或对应资源最终是否加载成功。

`0x1001a1a0` 还在 `objsys!0x10063f28` 和 `0x10063f8e` 被调用；这些调用同样不构成运行时执行或网络访问证据。由此不能确认认证、文件获取、解包、游戏大厅初始化或可操作游戏场景已成功。
