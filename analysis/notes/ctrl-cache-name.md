# `com/ctrl.fcc` 的 `cache` 成员证据

目标是解释 `com/ctrl.fcc` 偏移 `0xb2a` 的 FC0A 类型 6 哈希
`0x1bc7abd3`，以及为入口继续执行提供可验证的实现边界。以下结论来自
本地解码资源和 `CLIENT/objsys.dll` 的反汇编；没有把占位字段当作完整渲染器。

## 名称闭合

- `internal/symbol.StringTableHash("cache")` 的结果是
  `0x1bc7abd3`。
- `go run . -client CLIENT tokens com/ctrl.fcc` 在 `0xb2a` 显示该哈希。
- 同一哈希还出现在许多 UI/view 脚本中，形式均为 `cache = 0;`，例如
  `ui/ui`、`com/scroll_c`、`lobby/client`、多个 `team2003` 对话框和
  `act/fight` 地图脚本。这说明它是通用视图成员，而不是 `ctrl.fcc` 私有变量。
- `CLIENT/objsys.dll` 的注册表同时有一个名为 `wndcache` 的独立对象类；
  该字符串位于 `0x100a35ac`，注册代码在 `0x1005f7cb`。它与 `cache`
  成员不是同一个名字或同一对象。

## 原生读写证据

`view` 类在 `CLIENT/objsys.dll` 注册代码
`0x1005f2a3–0x1005f2cb`，对应构造入口 `0x1003a350`。

- 构造/初始化函数 `0x10038b40` 在 `0x10038b1b` 写入
  `this+0x7d4 = 1`，因此默认缓存开关为真。
- 写成员分派函数从 `0x10038be0` 开始，在 `0x10038c23` 比较
  `0x1bc7abd3`。命中后调用 FBase `#779` 检查值类型为整数
  (`1`)，再调用 `#778` 取出整数，写入 `this+0x7d4`
  (`0x10038c43–0x10038c4c`)，返回成功。
- 读成员分派函数从 `0x100391f0` 开始，在 `0x10039229` 比较同一哈希；
  命中后读取 `this+0x7d4` (`0x10039247`)，转为脚本整数返回。

## 对渲染的影响

- `0x1003a290` 的视图更新/绘制路径读取 `this+0x7d4`
  (`0x1003a2fb`)。
- 非零时调用视图缓存合成辅助函数 `0x1003a730`
  (`0x1003ae58–0x1003ae71`)；为零时跳过该辅助函数，直接走底层
  绘制路径 (`0x1003ae76` 起)。
- 因而入口中的 `cache = 0` 应实现为整数成员并保留到视图状态；在尚未
  接入完整帧缓存时，至少不能把它当作未知名称或布尔类型错误。

## 实现建议

在 Go 的 `Wnd`/`View` 公共成员处理中增加独立的 `Cache int32` 字段：

1. `NewWnd`/`NewView` 默认设为 `1`，与原生 `view` 构造函数一致。
2. `ReadMember(0x1bc7abd3)` 返回 `Kind: "int"` 和该字段。
3. `WriteMember(0x1bc7abd3, int)` 保存原始整数并标记重绘；非整数应报类型错误。
4. `View` 的实际绘制器完成后，再依据 `Cache != 0` 选择缓存合成或直接绘制；
   当前仅为启动链继续执行时，不应宣称缓存渲染已经完成。
