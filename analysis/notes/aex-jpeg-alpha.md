# AEX 的 JPEG 透明度平面

`CLIENT/in/img/map/root/land_02.ale` 是 AEX，而非 ALE v3。
头部模式3，描述符2条，两个加密图像载荷长度为16368和3630。
按既有 AEX 密钥相减解密后，两段均为550×202的 JPEG。
第二段虽然以3分量编码，但 Go JPEG 解码后每个像素都满足
R=G=B，且完全不透明；测试检查全部111100个像素。

FBase #69（`0x100296b0`）的模式3分支在
`0x10029912–0x1002995d` 经 #448 将第二图像段封装为内存流，
再调用 #439，参数1。随后 `0x100299b3` 起逐字节读取透明度，
进行已恢复的阈值和特殊像素预处理。这条路径没有把载荷限制为 GIF。
该观察结合真实资源，支持增加灰度 JPEG 内容的透明度平面。

Go 继续使用已存在的 JPEG 解码器。后续已确认默认加载先转为
RGB565，再经 #439(1) 将补零通道作整数平均；灰度输入也会发生
低位量化。彩色不透明平面可以按该路径转换，自身带透明度的位图
仍明确拒绝。完整指令与原生函数仿真见
[透明度平面转换](aex-alpha-conversion.md)。

两个帧分别为130×99和275×202，第二帧偏移(-79,-57)。
这些是资源解码和裁剪结果，不是屏幕像素。原版 JPEG 解码的舍入、
最终混色尚未验证。格式4到格式1的转换已覆盖全部65536个输入，
但该仿真不验证原版 JPEG 解码器的输出。
