# objsys 内置回调登记证据

本文只记录 `CLIENT/objsys.dll` 的静态登记代码和 `analysis/disassembly/objsys.annotated.asm` 可直接支持的结论。没有执行原程序，也没有连接历史服务器。PE 地址按反汇编中的 VA 记录。

## 登记格式

`0x1005ab10` 是通用回调登记函数。调用点先压入回调地址，再压入名称指针，然后调用登记函数。例如 `0x1005a284` 附近：

```asm
push 0x100a2d8c    ; "CreateObj"
push 0x10058d70    ; 回调地址
call 0x1005ab10
```

结合 `0x1005ab10` 本体，登记函数从名称计算 `FBase.dll!#858` 哈希（映射参数为 0），建立记录并写入 `0x10121c74` 指向的映射。记录字段为：

| 偏移 | 内容 |
| --- | --- |
| `+0x00` | 名称哈希 |
| `+0x04` | 名称字符串指针 |
| `+0x08` | 回调地址 |

插入操作调用 `FBase.dll!#282`。因此可用于 Go 调度的可靠主键是 `StringTableHash(名称)`；不要把脚本中的任意类型 6 哈希都直接解释成内置函数，也不要把插件类 ID 当作该哈希。

## CreateObj

| 名称 | 名称字符串 VA | 登记回调 VA | 登记哈希来源 |
| --- | ---: | ---: | --- |
| `CreateObj` | `0x100a2d8c` | `0x10058d70` | 登记时对 `"CreateObj"` 调用 `FBase #858` |

在回调 `0x10058d70` 中可见：

- 从脚本 VM 值读取第二个栈参数（反汇编函数序言后为 `[esp+0x30]`）；仅接受值类型 3 或 6。
- 类型 3 路径读取该值的字符串/哈希；类型 6 路径先解引用变量，并要求解引用结果类型为 3。
- 随后将所得值交给 `0x10065890` 查找/构造对象，并把对象与原 VM 值关联；失败路径通过 `FBase #842` 输出错误文本。
- 该函数按普通 `ret` 返回，参数清理由调用方处理。

这些证据说明它是基于 VM 参数动态创建对象的回调，但还不足以恢复其所有异常语义或完整 ABI。Go 当前并未据此声称复现该原生回调的全部签名；`new name(args)` 的构造调用约定另据编译器分派路径确认，见 [`new-constructor-call.md`](new-constructor-call.md)。

## Go 侧已恢复的纯内置函数

`internal/script/builtins.go` 中的 `RegisterCoreBuiltins` 按 `symbol.StringTableHash(登记名称)` 注册以下函数。参数个数和类型依据 `objsys.annotated.asm` 中的各回调校验分支及 FBase 辅助调用；字符串操作按原生 NUL 终止字节串处理，切片下标为字节索引，不是 Unicode 字符索引。

| 函数 | 原生回调 VA | 已确认的参数约束与行为 |
| --- | ---: | --- |
| `strlen` | `0x1004f860` | 1 个字符串参数；调用 `FBase #686` 取得长度并写回整数值 |
| `left` | `0x1004fc10` | 2 个参数：字符串、整数；`FBase #700` 按零基位置截短，位置小于 0 或大于长度时结果为空（`0` 得空串，等于长度得原串） |
| `right` | `0x1004fcf0` | 2 个参数：字符串、整数；`FBase #709` 先计算长度减数量作为起始位置，起始位置小于 0 或大于长度时结果为空（数量为 0 得空串，数量等于长度得原串） |
| `mid` | `0x1004fee0` | 3 个参数：字符串、起点整数、长度整数；`FBase #705` 使用零基字节位置，负起点按 0 处理，负长度延伸到末尾，末尾越界则截到字符串末尾 |
| `atoi` | `0x100502d0` | 1 个字符串参数；回调调用 `FBase #684`，其十进制路径调用 `FBase #683`（`0x1000e010`） |
| `str` | `0x10050360` | 1 个整数参数；调用 `FBase #673` 转换为字符串 |
| `abs` | `0x10051220` | 1 个整数或浮点参数；回调允许数值类型，浮点结果再依运行时标志决定写回整数或浮点值 |
| `min` | `0x100512b0` | 至少 2 个参数；逐项比较数值类型（整数或浮点），结果类型随参与比较的值而定 |
| `max` | `0x100513d0` | 至少 2 个参数；逐项比较数值类型（整数或浮点），结果类型随参与比较的值而定 |
| `RGB` | `0x100539c0` | 3 个整数参数；原生以红、绿、蓝顺序按 8 位移位并 OR 成一个整数，没有额外通道掩码 |

Go `Value` 当前没有浮点类型，因此 `abs/min/max` 暂只接受整数值；这不等同于原生完整数值语义。Go 侧参数数量或类型不符合上述约束时返回中文错误。`FBase #683` 的反汇编显示，十进制路径仅识别可选前缀 `-`，不跳过前导空白、不识别 `+`，至少一位十进制数字后遇非数字即停止；无数字时返回 0。累加使用 32 位寄存器指令且没有溢出检查，因此按 DWORD 回绕。对应实现对 C 字符串（首个 NUL 截断）恢复这些规则。`FBase #700/#709` 也都在切片边界失败分支显式构造空字符串，证实超长/负长度不会自动裁成全串。相关实现尚未覆盖异常/资源语义，也不意味着全局登记表中的其余函数已实现。

## index.fcc 中的三个哈希

`analysis/decoded/index/tmp.cod` 的 `tokens` 输出显示以下均为类型 6；PE 的已恢复内置登记段没有以这些值作为常量登记。现有字符串池匹配也没有给出名称。因此下表只记静态上下文，不将其强行映射到某个内置回调。

| 哈希 | 首次出现附近的 token 上下文 | 可确认结论 |
| --- | --- | --- |
| `0xdc331502` | `#system` 后，随后是类型 3 字符串 `FW@kele8_Ver103` | 已由系统指令分支及哈希核验确认为 `devcode` |
| `0xd53b302d` | `tmp.cod` 偏移 `0x4a` 的类型 6 符号哈希，紧随 `FW@kele8_Ver103` 和换行；后续为 `(`、类型 3 字符串 `..::版权所有FancyWorld::..`、`)`、`;` | 语法形态是裸 `NAME(string)` 调用；哈希对应的名称与接收对象未知 |
| `0x9eea611e` | 全 DLL NUL 分隔字符串扫描找到 `pdesktop`，并且 index 中此哈希重复处于成员访问左侧 | 由 Go `StringTableHash` 精确验证为 `pdesktop` |
| `0x6f297615` | 紧随 `pdesktop.`，其后赋值整数 `134` | 在 DLL NUL 分隔字符串和 index 字符串池中均未匹配；成员名称未知 |

在 `objsys.annotated.asm` 中，`0xd53b302d` 出现在两个窗口相关的成员写入分派路径：

- `0x10030330` 的分派函数以 `[esp+0x10]` 的哈希进入比较树；在 `0x10030749–0x10030754` 命中 `0xd53b302d` 后，分支 `0x100307c3–0x10030832` 从 VM 值取第二参数，`FBase #779` 要求其类型为 3（字符串），`FBase #808/#646` 取得文本指针，再以对象 `this+0xcc` 的 HWND 调用 `USER32!SetWindowTextA`。随后以对象、一个常量和 VM 值调用 `0x1005ab90`；普通完成路径在 `0x10030864` 将 `EAX` 清零，函数于 `0x1003087e` 用 `ret 0x0c` 清理三个栈参数。该函数还处理窗口位置、显示状态等其他分支。
- `0x10060da0` 的另一窗口成员分派函数在 `0x100620e7` 比较同一哈希；分支 `0x100620f3–0x10062143` 同样要求 VM 值类型 3，取得字符串后以对象 `this+0x1c68` 的 HWND 调用 `USER32!SetWindowTextA`。清理后汇入 `0x10062470`，普通返回值也是 `EAX=0`，函数在 `0x1006248a` 以 `ret 0x0c` 清理三个栈参数。两处证据都指向窗口对象的成员写入/属性设置分支，不是类型 6 名称调用回调本身。

上述两段最初按参数校验误称为“成员写入分派器”。继续核对虚表后，确认它们位于对象虚表 `+0x24` 的调用槽；真正的成员属性写入在另一个槽。两者均把该哈希映射到设置窗口标题文本的行为，并要求字符串参数。哈希对应的原始名称仍未找到，Go保留哈希，不命名为猜测的 `Title` 或 `SetTitle`。

### 裸调用的解释器执行分支

从启动入口继续静态跟踪：`0x10067de5` 调用 `0x10065fa0`，调用前将当前对象（`[ebp+8]`）置于 `ECX`，并把启动解析出的记录指针及四个零参数压栈。`0x10065fa0` 从当前记录偏移 `+4` 读取语句类型；类型 `0x0e` 在跳转表 `0x10067bf0` 的第 14 项转到 `0x100678d4`。

该分支对调用表达式作静态校验：表达式/调用槽要求类型 6 且元素数为 1；取第 0 项后要求类型 4 且元素数为 2，随后取出子值交给 `0x1000a5d0`。该辅助函数引用对象偏移 `+0x14` 的字段，并调用 `0x10017130`；后者再将内部对象及若干参数传给 `0x100128d0`，遍历相关记录并在结束时调用 `0x10015fc0`。这些调用显示有运行时调用记录处理，但当前反汇编不足以确定它们最终调用哪个宿主回调。此分支没有直接调用 `0x10030330` 或 `0x10060da0`，也没有可见的 `SetWindowTextA` 调用；目前这条反汇编链不能证明哈希 `0xd53b302d` 被解析成窗口成员 setter，亦不能证明它被登记表中的哪个全局回调接收。启动调用处的 `ECX` 是执行上下文，不足以单独证明它就是被调用对象或窗口实例。

上述追踪仅覆盖语句外层；下述补充追踪已找到调用记录与具体窗口分派的连接，不再把“裸调用未知”作为该分支的最终结论。

### 对象调用桥补充证据

`0x10017130` 遍历每条20字节表达式记录。记录类型0经 `0x100127a0` 压入28字节值栈；类型1调用记录 `+8` 的函数指针；类型2调用 `0x10015eb0` 解析栈顶值。`0x100128d0` 仅初始化求值器上下文，并不负责遍历。

编译器 `0x10016ce0–0x10016e05` 处理括号结束并生成类型2记录；调用运算符7由 `0x10016261` 登记到 `0x1011d1ec`，回调地址为 `0x10013f20`。该回调取参数值和类型7的名称槽，在 `0x10013fd1` 读取名称哈希，以名称槽 `+0x14` 的对象作为 `ECX`，调用 `0x1005ad10(caller, hash, args, flags)`。

`0x1005ad10` 暂存并替换对象 `+0x90` 的调用上下文，`0x1005adf2` 用相同对象调用虚表 `+0x24`，实参为哈希、VM值、标志。仅返回1时才继续 `0x1005a3f0` 的脚本方法查找。桌面虚表 `0x100a39c0` 和真实根对象虚表 `0x100a3bb0` 的该槽分别存于 `0x100a39e4`、`0x100a3bd4`，两者均指向 `0x10060da0`。原始PE表项可以独立核对，不依赖把哈希解释成某个名称。

`0x10060da0` 在 `0x100620e7` 比较 `0xd53b302d`，命中后经 `0x100620f3–0x10062143` 取得字符串，使用对象 `+0x1c68` 的 HWND 调用 `SetWindowTextA`。分支返回0而且不改写VM参数。`0x10013f20` 成功后将参数值复制回表达式结果。因此Go标题分支返回原传入字符串，不把原生的状态码0误当作脚本返回值。

未知哈希从 `0x100623e5` 进入 `0x1005a770`；该函数在 `0x1005a7d3–0x1005a868` 查询已登记的全局回调表。该路径还包含其他对象/接口查找，尚未完整移植。Go目前支持未绑定名称的当前宿主对象分派、显式宿主对象成员调用和已实现全局函数回退；类、接口、脚本方法查找及全部优先级仍未恢复。

`analysis/tools/oracle_root_dispatch.py` 与 `analysis/evidence/root-dispatch-oracle.json` 通过 Unicorn 从 `0x1005ad10` 执行真实指令，经两张虚表到达标题分支，分派状态返回0，合成VM值未变化。FBase值访问/清理和 `SetWindowTextA` 使用明确模型hook，未验证真实VM ABI或创建Windows窗口，也未执行 `0x10013f20` 包装器的结果复制链；包装器返回参数值的结论来自前述静态证据。

`internal/objsys/desktop.go` 接收标题原始字节，按原生C字符串处理首个NUL；没有窗口后端或后端失败时明确报错。完整启动先执行 DLL 内嵌 `SYSTEM.COD`，已经构造系统 ToolTips 和文字子对象、准备 AEX 帧数据并注册提示窗口。DateCmp 的 tuple 结果在 `>` 比较产生原生错误8，桌面构造器忽略该已知系统脚本错误并继续 index。标题、字体、尺寸设置、空绑定标记、自动宽高、RegInterface、`halign`/`valign`、`pointmode` 与 JPEG 相关路径已接入。`imgex` 工厂和 `src` string / string,int 形态已实现；JPEG 资源可加载并读取 800×600 源尺寸，AEX 灰度 JPEG 透明度平面也可解码；资源名转小写，整数参数乘 2 后保留为资源查找参数，不解释为缩放比例。这些能力不证明资源已绘制到屏幕。

`index.fcc:0xc38`、`0xcc8`、`0xd7c`、`0x1acc`、`0x1670`、`0x2924`、`0x2f1e` 为已越过的历史边界。后续场景绘制、输入、登录、玩法仍未恢复或验证；当前没有绘制场景或进入游戏的证据。路径映射 `0x112e4b8f`、资源目录读取 `0xaf665c57`、HTTP 重试和目录解析均已有实现；缓存位于独立 `os.UserCacheDir()/qy-fcrunner`，但当前每次重取，缓存有效性校验尚未恢复。FC0A 编译数据保持原始字节而不拆行，XY20 多 CAB 成员按顺序拼接；目录条目按原生规范化哈希覆盖，不做完整路径比较。

`0x6f297615` 在 `0x100601e0` 起始的成员写入分派器和 `0x100604e0` 起始的成员读取分派器中各有对应分支。写入分支要求 VM 值类型为 1（整数），取出整数写入数据导出 `FBase #421` 的全局存储，并调用 `FBase #450` 重建字体；读取分支把同一全局整数经 `FBase #748` 写回 VM 值。结合系统 `charset` 分支现已确认它对应字体字符集，不是来自 `FBase #424` 的系统显示字符集。`#421` 是数据槽，不是函数调用。

`#450` 位于 `0x10023140`，依次删除旧的 `#454/#455` 字体句柄并用 `CreateFontA` 重建。普通字体在显示字符集不是136时高12宽6、weight400；显示字符集136时高13宽0；小字体采用 `Small Fonts`。Go后端以系统中文TTF/TTC、12像素普通face和10像素小face重建，并将GBK/Big5字节解码后栅格化；不声称与GDI的字体匹配、固定字宽和像素输出一致。字体更新失败保留旧Go状态并报错，属于宿主错误处理选择。

`pdesktop` getter 及对象标识/指针的独立证据见 [pdesktop-binding.md](pdesktop-binding.md)。Go将它作为只读宿主属性返回当前桌面对象，不用可任意覆盖的全局变量模拟。宿主引用把读写拆开：简单赋值不读getter，复合赋值和自增减均只读取一次、写入一次。

## 对 Go 调度器的可用边界

- 可以按 `StringTableHash(登记名称)` 建立 `name/hash -> Go callback` 表；登记名称、原生回调 VA 与 `CreateObj` 的记录字段都有静态证据。
- 精确脚本回调签名仍未知。原生回调使用 objsys/FBase 的 VM 值对象、引用计数、模块上下文和宿主状态，不能把 PE 回调 VA 当作普通 C 函数签名。
- 对未知原始名称保留哈希；只按已确认的调用/属性行为实现，不绑定猜测的函数名。标题操作已有上述调用桥证据，字体已接入跨平台 Go 后端；不声称其像素输出与原生 GDI 一致。
- 仅实现登记表并不能让客户端进入游戏；解释器、对象系统、窗口/图像/ALE、网络和插件运行时仍需逐步恢复。
