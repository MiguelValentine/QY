# ALE v3 颜色转换证据

本记录沿用 `analysis/evidence/fbase-disassembly.json` 和 `analysis/disassembly/fbase.annotated.asm`，并补充单函数仿真。它不代表原版客户端或完整图形系统已运行。

## 格式4到行编码器

- FBase #72（`0x1002d450`）在 `0x1002d500–0x1002d52e` 检查输入图像格式是否为4；否则用 #345 创建格式4图像，并调用 #344 转换。
- `0x1002d5b1–0x1002d5ce` 将该图像像素指针按每项两字节计算，传给行编码器 `0x1002d160`。因此行命令中原样保留的 `u16` 来自格式4像素。
- #345（`0x1001d630`）的格式4分支 `0x1001d6a6` 采用每像素两字节。
- #344（`0x1001dc10`）在 `0x1001dcb4–0x1001dd0d` 将格式7转为格式4时调用 `0x1001aac0`；反向分支 `0x1001dd1f–0x1001dd75` 调用 `0x1001ab10`。

`0x1001aac0` 用 `F800/07E0/001F` 掩码将32位颜色打包为 RGB565。`0x1001ab10` 的逆转换补零低位，得到小端 BGRA：

```text
R = (raw >> 8) & 0xf8
G = (raw >> 3) & 0xfc
B = (raw << 3) & 0xf8
A = 255
```

这里不能用将5/6位颜色按位复制扩展到255的常见实现替代：原生白色转换结果为 `(248,252,248,255)`。

## 原生转换全值域对照

`analysis/tools/oracle_ale_colors.py` 将原始 `CLIENT/fbase.dll` 映射到首选地址，用 Unicorn 执行 `0x1001ab10`。栈参数依次是目标指针、目标行余量、源指针、源行余量、宽和高；使用宽65536、高1、两个行余量均为0。

`analysis/evidence/ale-color-oracle.json` 保存 DLL 身份、仿真器版本、参数及结果。输入覆盖全部65536个 `u16`；原生输出与公式逐字节一致，输出 SHA-256 均为 `8e661678d463a3920aa7ce057cb1726ec4c9be0d27d8834034c2890a554f381c`。该函数无外部调用，不需要挂钩颜色转换或模拟 DLL 初始化。

## Go 预览边界

`internal/ale.Color565` 对应上述转换；`Frame.Preview` 按行表定位跳行，将普通 `u16` 命令转换为 NRGBA，采用行解码器的量化 alpha 代表值。预览画布只包含帧宽高，不应用帧偏移。尺寸和总像素数有上限。

`0x11` 特殊段没有原始 `u16`，因此不能从该命令恢复颜色；预览遇到这类可见像素会明确报不支持。alpha 量化、原生混色、特殊绘制模式、ALE版本1/2、AEX及完整磁盘加载链仍未恢复。

CLI 的 `image <资源.ale> <输出.png> [帧序号]` 可导出受支持的帧，序号从0开始，拒绝覆盖已有输出。真实 `act/img/bullet/bullet.ale` 第0帧已经成功导出7×7 PNG；此结果只是资源预览。
