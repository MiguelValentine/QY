# `CallSub` 原生行为核对

本文核对 `objsys.dll` 的 `CallSub` 回调及其依赖的 FBase 值操作。证据来自保存的 PE 反汇编，不是原版客户端动态运行。关联 REA Evidence：`objsys-disassembly.json`（`ev_79268ca8fa4f56c3fa122adeae94d4774f186500c9d5deb328525b66ac46cbaf`）和 `fbase-disassembly.json`（`ev_5fc95fa046397bf605b945fbf373993a52efed99a223a6fc52164b61aa8a1e0a`）。下列地址是模块基址 `0x10000000` 下的 VA。

## 入口和参数

- `objsys:0x1005a254–0x1005a25e` 将 `"CallSub"` 登记到回调 `0x10058630`。
- 回调先要求实参值类型码为 6（tuple），再要求至少 3 项。#784 分别取索引 0 并要求类型码 3（字符串）、取索引 2 并要求类型码 3。索引 1 的值被复制到临时 VM 值，作为候选对象匹配值。没有 extra 时事件参数值保持 null；恰好一个 extra 时，#784 将索引 3 原样复制为事件参数值，未强制包装成 tuple；两个及以上 extra 时，索引 3 仍先原样复制，此后索引 4 起才经 #759 追加。#759 在首个 extra 为标量时将其与下一项组成 tuple；首个 extra 本身为 tuple 时则对该 tuple 值执行追加路径。
- `index.fcc:0x42ec` 的调用为 `CallSub("m_nMid", 1, "DelThis")`。按上述实参位置，名称是 `"m_nMid"`，比较值为整数 `1`，派发事件名是 `"DelThis"`。
- 参数类型或数量不符合入口检查时，回调返回状态码 2。正常处理路径最终返回 EAX=0；已处理事件数另被写入返回 VM 整数值。

## 候选遍历、虚调用和派发

- 回调从当前对象 `+0x94` 子列表取首项（FBase #520），以 #525 推进，直至列表耗尽。代码只沿这个列表迭代，没有发现递归子树遍历。
- 候选对象 `+8` 的标志位 bit 0 为 1 时跳过；bit 0 为 0 才继续。
- 对剩余候选，回调以 FBase #646 从名称 VM 值取得字符串 payload 地址，并按顺序压入该地址、名称哈希、0 和输出 VM 值槽地址，最后以候选对象为 `this` 调用虚表 `+0x34`。`wnd` 构造器写入 vtable `0x100a3270`，其 `+0x34` 槽指向 `objsys:0x1004d6b0`；该函数的常规属性路径按参数 2 的 hash 查成员，命中时通过 #747 将成员 VM 值复制到参数 4 输出槽并返回 1。参数 3 在这个 getter 路径未使用。其他类的同槽实现未逐类确认。
- getter 返回非零后，回调以 FBase #750 比较输出槽中的候选属性值与输入 tuple 的索引 1 值；比较相等才调用 `objsys:0x1005ab90`。派发的目标对象是候选对象，事件名来自输入 tuple 的索引 2。extra 参数按前述规则传递：一个 extra 原样传值；多个 extra 时从第二项开始经 #759 追加到首项值。#5ab90 返回非零时才递增已处理事件计数。
- 完成遍历后，FBase #748 将已处理事件数写成返回 VM 整数值；type 1 分支将整数 payload 以 XOR `0xF0A0` 编码存储。原生 callback 本身仍以 0 结束。#5ab90 的布尔返回表示此次事件是否被处理；不应将其与“属性值比较命中”混为一谈。

## FBase 值语义

- #784（`fbase:0x10014340`）仅接受 tuple 类型码 6、非负且小于 tuple 长度的索引。常见 tuple 类型码 6 和扩展 tuple 类型码 `0x1a` 使用 12 字节步长读取内嵌元素；其他 tuple 存储形式从元素指针表取值。取得后调用 #747（`0x10014070`）复制 VM 值。
- #747 对类型码 1 的值复制整数 payload；字符串/tuple 等引用 payload 按其引用计数规则增加引用；类型码为 0 的值按原生全局空值路径处理。因而 `CallSub` 取索引 1 是复制 VM 值，不是仅保存其临时地址。
- #779（`fbase:0x10001110`）直接返回 VM 值首 DWORD，即原始 type tag，没有将外部标签映射成另一套内部标签。因此这里由参数检查确认的字符串是 raw type 3。#750（`fbase:0x10013820`）先要求两个 raw type tag 相同，再按标签处理：type 0 相同即相等；type 1 比较 +4 的 32 位整数 payload；type 2 比较 +8 开始的 8 个字节（逐 16 位比较）；type 3 比较 +8 的 32 位 DWORD；type 4 按字节比较两个 payload 指针指向的 NUL 结尾缓冲区；type 5 先比较元素数量，再递归调用 #785 取对应元素并用 #750 逐项比较；type 6–8 落到不相等分支。故 #750 的 type 4 字节串分支不能据此称为 #779 暴露的脚本字符串类型；raw type 3 的等值规则是 +8 DWORD 比较，不是该字节串循环。type 2–4 的业务类型名称不由这些比较指令单独确定。

## Go 对照与边界

Go `script.Value` 以 `Kind`、`Integer`、`Text`、`Items`、`Object` 等字段保存值；当前 `binary` 只实现 int/string 的 `==`、`!=`，tuple 等类型仍报未恢复运算类型。因此若实现 `CallSub`，不能直接复用当前脚本二元比较来替代 #750；先支持整数筛选时应实现 #750 raw type 1 的 DWORD 相等规则，并让属性 getter 显式返回输出值槽结果。`CallSub` 本身目前不等同于 Go 中已完成的事件枚举能力。

这些是反汇编所支持的静态结论；没有证明所有对象类 `+0x34` 实现都遵循同一业务语义，也没有动态验证事件参数生命周期、异常路径或执行时子列表变化行为。
