# `newtip.fcc` 初始成员名候选与原生登记

## 范围与方法

本笔记核对 `CLIENT/com/newtip.fcc` 中第一个 `<class>` 定义至偏移 `0x7c4` 的 `<class>` 对象节点之间的成员赋值/调用，并补充 `index.fcc` 的初始窗口尺寸设置。标记偏移来自 `go run . tokens com/newtip.fcc` 与 `go run . tokens index.fcc`；候选名称由 `go run ./analysis/tools/symbol_lookup <hash> CLIENT/objsys.dll CLIENT/fbase.dll` 扫描 NUL 结尾可打印字符串所得。字符串哈希命中只表示 DLL 中存在同哈希字符串候选，不单独证明属性绑定。绑定证据另以 `objsys.dll` 原生登记代码的名称指针、getter/setter 回调登记为准。所有地址是静态反汇编 VA，不是运行时观察。

## 启动脚本中的初始窗口设置

`index.fcc` 偏移 `0x6e` 的哈希 `0x9eea611e` 与 DLL 字符串候选 `pdesktop` 相符；偏移 `0x110` 的 `0x96712ccc` 与候选 `size` 相符，赋值为 `(800, 600)`。原生桌面表在 `objsys.annotated.asm:1004f08d–1004f099` 以名称 `pdesktop` 登记 getter；窗口表在 `1004f16a–1004f187` 以名称 `size` 分别登记 getter `0x1004da50`、setter `0x1004e290`。结合 [桌面启动成员笔记](desktop-startup-members.md)，此处是 pdesktop 的逻辑尺寸属性写入；底层窗口尺寸还会经过对象缓存几何差值补偿。证据分别是哈希候选和原生登记，不由脚本中的变量名推断。

### `wnd` 工厂查找与 `pid` 的字段关系

`objsys.dll` 的 `0x1005f070` 是对象工厂查找路径之一。它先以请求类名值（来自 `[esp+0x14]`，在此函数中保存到 `EDI`）查询 `0x10121e84`；命中后才以键 `0xf433a6a4` 查询 `0x10121e54` 并调用所得回调。符号扫描将 `0xf433a6a4` 命中为字符串候选 `userdll`。若第一张表未命中，函数会改为直接以请求类名值查询 `0x10121e54`。因此 `userdll` 只是第一张表命中后的二级路由键，不是两张表共同使用的首次查找键。

后续核对已闭合 `wnd` 工厂链：`0x1005f15d` 传入名称指针 `0x100a370c`（文件偏移669452的字符串 `wnd`），以 `ECX=0x10121e54` 调用 FBase #310 取得登记槽；`0x1005f185` 向空槽写入工厂 `0x1005e1d0`。工厂分配 `0xc8` 字节并调用构造函数 `0x1005d720`。构造路径在 `0x1005d773–0x1005d777` 将传入所属对象写到 `+0xa8`，初始化零矩形、`+0x1c=1` 和 `+8=2`，在 `0x1005d868–0x1005d893` 将自身插入所属对象的子容器，并将 `wnd` 哈希写到 `+0x0c`。该路径创建引擎逻辑对象，未见创建独立顶层系统窗口。

Go 工厂现保存逻辑尺寸、层次顺序、显示状态和父子链。`show` getter `0x1004dde0` 对显示位作算术右移，真值为 `-1`。宽高 setter `0x1004e230`、`0x1004e260` 同时更新原生失效标记；Go 暂以 `Dirty` 表示布局变化，完整绘制和事件分派仍待恢复。当时的真实资源测试已越过 `pid=pdesktop`，并在偏移 `0x62` 因名称尚未识别而暂停；这只是旧测试边界，不是当前语义边界。后续 [newtip-zorder-name.md](newtip-zorder-name.md) 已将 `0x81e69173` 闭合为 `ZTOP`，宏值为 `0x6fffffff`；`bk`/`himgtile` 的调用及资源路径也已由 [newtip-background-call.md](newtip-background-call.md) 补齐。上述为静态分析与当前 Go 代码状态说明，不构成原版运行时观察。

`pid` 的绑定证据现可进一步确认。在 `0x1004f033–0x1004f049`，原生对象成员表以名称指针 `0x100a2258` 将 getter `0x1004d7d0` 登记到对象；紧接着在 `0x1004f049–0x1004f055` 又以相同名称登记 setter `0x1004df40`。此前的 DLL 字符串扫描把该名称指针解析为 `"pid"`，而同一成员登记序列中明确标注了 `pcaller`、`pcon` 等后续属性名。

getter `0x1004d7d0` 读取接收对象 `+0xa8`；非空时把该对象及其 `+4` 值交给 FBase #799，空值分支则向 #799 传入空参数。因此 getter 暴露的是该 `+0xa8` 关联对象。setter `0x1004df40` 先调用 `0x1005bd10` 解析参数；失败时报告 `"not find obj,can't set pid."`。成功后经 FBase #782 取出对象，沿该对象的 `+0xa8` 链查找当前接收对象；若找到则报告循环错误并拒绝。否则 setter 将当前对象原有 `+0xa8` 关联从原容器移除，写入新对象到当前对象 `+0xa8`，并将当前对象加入新关联对象的容器（`0x1004df86–0x1004dfdf`）。这为 `pid` 与 `+0xa8` 所属/父链的关系提供了直接静态证据；字段的完整 C++ 类型、#799 的值编码和具体 UI 层级后果仍未知。

上述 `pid` 登记片段来自通用原生对象成员初始化路径，不能据此认为它是 `wnd` 类独有属性。Go 真实资源测试及图形启动现已越过该赋值；这只验证当前重建的执行结果，没有验证原版运行时。

### 自引用与根对象尺寸读取

`0x1004f0af–0x1004f0bb` 以名称 `this` 登记 getter `0x1004d940`。后者将接收者和接收者 `+4` 标识交给 FBase #799；Go 对桌面及逻辑 `wnd` 返回各自的对象引用。宽高 getter `0x1004db90`、`0x1004dbb0` 分别计算 `+0x2c - +0x24`、`+0x30 - +0x28`，与 `size` 同源。Go 的桌面宽高读取委派给实际尺寸后端，后端缺失或失败时保留错误，不能从常数猜测尺寸；逻辑子窗口仍读取各自布局值。

## `parent` 与其他边界

上述 `com/newtip.fcc` 区间没有名为或哈希候选为 `parent` 的显式成员赋值/调用。对本区间出现的哈希运行现有符号查询也未发现 `parent` 候选。故不为 `Form` 或 `wnd` 臆造 parent 字段；对象是否通过未显示的宿主关系设定父窗口，需要另有创建/布局证据。

符号查询是针对 DLL 中 NUL 结尾可打印 ASCII 串的哈希匹配；短串如 `s`、`w`、`this` 尤其可能有歧义。登记表证据只说明原生代码用对应名称登记了回调，不保证 FCC 中任一同哈希出现都具有同一对象上下文或成功执行。未运行原版客户端；本记录不覆盖对象创建器、回调派发和窗口层级实现。
