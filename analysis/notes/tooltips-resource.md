# TOOLTIPS.ALE 内置资源验证

`objsys.dll` 的 PE 资源项 `IMG / TOOLTIPS.ALE / 2052` 可由 `readPEResource` 精确读取。数据位于文件偏移 `842104`，长度 `990` 字节，SHA-256 为 `03600b4d0c9c8ebc222a8092479841dfab92e29adf680222b621d9207c5a4b04`；与资源清单一致。

内容开头是 `AEX\0`，不是 `ALE\0`。`internal/ale.Parse` 是 ALE v3 解析器，对这个资源仍返回 `ale.ErrUnknownFormat`。`internal/objsys` 资源加载已按签名分派到独立的 `ParseAEX`，解密容器并解码两个 GIF 平面，再调用 `PrepareFrames`，形成三帧可供绘制器消费的数据。没有将 AEX 当成 ALE v3 的行表或行命令。

原始字节在偏移 `0x04..0x0b` 为 `CA:BBL:<`；偏移 `0x0c`、`0x10`、`0x14`、`0x18`、`0x1c` 的小端 DWORD 分别为描述符数 `3`、格式值 `3`、两个 GIF 长度 `498` 与 `388`、后续字符串/字典块长度 `0`。后续块的具体编码和非零时的边界规则仍未确认；当前 Go 解析器遇到非零长度会返回 `ale.ErrUnsupported`，不会把它当作 GIF。

FBase 导出 `#78`（`fbase.annotated.asm:59408` 起）是 ALE 序列化写入函数：`0x100276ca` 写入 `ALE\0`，随后写版本、长度、帧块和 `END\0`；这不能说明该资源就是 ALE。读取路径实际由 FBase 导出 `#68` 和 `#69` 处理，入口分别为 `0x10029f90` 与 `0x100296b0`（`fbase.annotated.asm:62759`、`62044`）。

`#63` 在 `0x1002a5f9` 将扩展名与 `0x10058328`（`.rdata` 字节为 `ale\0`）比较。命中时，`res$` 分支在 `0x1002a884–0x1002a895` 用 `#484`（`0x10008a30`）从 `IMG` 类型 PE 资源装入字节流，随后于 `0x1002a8a1` 调用 `#68`；这条分支不经过 `#449` 或 OLE 图片加载。`#68` 先用 `#482` 读取 4 字节，并将前三字节与 `0x10058300` 的 `ALE\0` 比较。匹配时进入 ALE 解析主体；不匹配时调用 `#69`。因此本资源的 `AEX\0` 路径是 `#63 -> #484 -> #68 -> #69`。

`#69`（`0x100296b0`）将输入前 4 字节与 `0x100582f8` 的 `AEX\0` 比较；接着读取 8 字节标记，并读取 20 字节头部。对 `TOOLTIPS.ALE`，头部观测值为帧记录数 `3`、格式值 `3`、两个 GIF 长度 `498`、`388` 和后续块长度 `0`。之后读取 `3 * 24` 字节帧记录，再读取两个非空 GIF 数据块。记录的六个 DWORD 会传入 `#77`（`0x1002da40`）构造帧；当前闭合的顺序为 `[width,height,x,y,offsetX,offsetY]`，含裁剪增量的偏移写入见 [帧映射](aex-frame-mapping.md)。

头部 8 字节标记若不等于 ASCII `00000000`，`#69` 会调用 `0x10027410` 对各数据块逐字节执行 `数据字节 - 标记字节[i mod 8]`，按 8 位回绕。该资源的标记为 `CA:BBL:<`。对两段数据应用此变换后，结果分别以 `GIF89a` 开头；`#69` 将它们分别交给 `#448`（`0x10023e70`）的 GIF/JPEG 图片装载路径。两平面均为42×30完整单帧 GIF。Go 已恢复模式3的 RGB565 量化与灰度预处理，得到1260个编码前像素，其中43个带原生暗色特殊标记。帧切分结果为20×30、8×30、14×30，偏移依次为(-1,0)、(0,0)、(0,0)，加载回归也验证43个特殊标记在切分后保留。特殊标记的最终绘制效果、原生有损行编码和所有模式尚未恢复，不能将这些数据直接视为普通 RGBA 或宣称提示背景已经画出。

所以此前“`AEX\0` 被直接送入通用 OLE 图片链、未见解包”的结论不正确：该 `.ale` 资源走 `#68` 的 ALE/AEX 双格式分派，再由 `#69` 解密嵌入 GIF 并构造动画帧。资源名后缀仍不代表文件内容符合 ALE v3；现有 `internal/ale.Parse` 也未因此自动获得 AEX 支持。静态反汇编证据记录为 `ev_5fc95fa046397bf605b945fbf373993a52efed99a223a6fc52164b61aa8a1e0a`，PE 资源清单证据为 `ev_39c4876f1d896585d3fc56f35416264c4e08b1475ab3ba32789f18878133b5cd`；两者均不代表运行时观测。
