# `files_dir.dz` 读取与失败路径

## 范围与证据

本文仅追踪 `objsys.dll` 中由 `0x1001a1a0` 调用的 `0x1001a0a0`，以及读取路径上的直接 helper；不运行客户端、不访问网络。主要证据为 `objsys-disassembly.json`（Evidence `ev_79268ca8fa4f56c3fa122adeae94d4774f186500c9d5deb328525b66ac46cbaf`）与 `fbase-disassembly.json`（Evidence `ev_5fc95fa046397bf605b945fbf373993a52efed99a223a6fc52164b61aa8a1e0a`）。反汇编文本位于 `analysis/disassembly/objsys.annotated.asm` 和 `analysis/disassembly/fbase.annotated.asm`；下文地址均为各 DLL 基址 `0x10000000` 下的 VA。

## 调用链与结果

入口 `objsys!0x1001a0a0` 接收路径，并在 `0x1001a0da` 调用 `objsys!0x100190c0`。若该 helper 返回零，入口记录 `"Can't GetTextImm %s"`，清理临时字符串并在 `0x1001a157` 返回 `EAX=0`；成功则从准备好的字符串取值，在 `0x1001a130` 调 `objsys!0x10018000`。后者失败时记录 `"Load text file %s err"`，并经 `0x1001a144–0x1001a168` 返回 `EAX=0`；成功则入口在 `0x1001a169–0x1001a190` 返回 `EAX=1`。

调用者 `objsys!0x1001a1a0` 在 `0x1001a28a` 调 `0x1001a0a0`，随后 `0x1001a292` 检查返回值。零值直接跳到 `0x1001a526` 的清理路径，跳过后续 FBase #216 条目枚举；非零才继续 #216、#729 及对象登记。更外层桌面分派器 `objsys!0x10061cbe` 调用 `0x1001a1a0` 后不检查其返回值，清理参数并继续公共出口。因此，资源目录读取失败会跳过这次条目解析，但不会仅凭此返回值中止这条宿主分派路径。

## 本地读取与格式

`objsys!0x10018000`（`0x10018018–0x10018038`）初始化 FBase 文件流并以输入路径调用 FBase #209。FBase #209（`fbase!0x10009750–0x10009810`）最终调用 `KERNEL32!CreateFileA`，使用只读访问和 `OPEN_EXISTING`；空句柄或 `INVALID_HANDLE_VALUE` 均返回零。此后读取通过 FBase #211（`fbase!0x10007e60–0x10007e99`）调用 `KERNEL32!ReadFile`。因此 `0x10018000` 确实从本地文件路径读数据，不是 HTTP 下载函数。

`0x10018000` 将文件内容交给 `objsys!0x10017b50`，后者先读长度与最多 4 字节文件头。文件长度小于 4 时，它把原始字节读入缓冲区；否则按 `"XY20"`、`"!CD1"`、`"FC0A"` 分支处理。所有最终追加数据的 FBase #132 调用都是按给定字节数追加到字节缓冲区；其本身不拆行。

`XY20` 路径（`0x10017c39–0x10017df6`）使用 FBase #492 将 CAB 源读入内存，再调用 `objsys!0x100179a0` 初始化 CAB/FDI 状态。`0x100179a0` 通过 `FDICreate` 与 `FDIIsCabinet` 读取 CAB 元信息，其中 `cFiles` 用于初始化成员名数组；随后通过 `0x10017810` 和 FDI 通知回调枚举成员名。`objsys!0x10017b50` 随后再次调用 `0x10017810`，以另一模式执行提取。两种模式在 `objsys!0x10017770` 的 COPY_FILE 回调中分流：枚举模式记录成员名并返回 0（跳过写出）；提取模式返回同一个共享输出流。回调没有按成员名筛选或只选择某一项的逻辑；各个被提取成员的数据都通过 FBase #490/#485 写到该共享输出流，故输出是按 CAB 通知顺序连续拼接的成员内容，中间没有额外分隔符。随后 `0x10017d8e–0x10017dac` 检查拼接结果是否以 `"FC0A"` 开头：相等时设置状态 5 并按原长度追加完整缓冲区；不等时在末尾补 NUL 后追加文本缓冲区。静态证据不支持剥除 FC0A 头、只解出 CAB 第一个成员或选取特定成员。

`"!CD1"` 路径调用 FBase #492 解码。`0x10017eee–0x10017f0c` 检查解码后的 `"FC0A"`：相等时设置状态 5，追加完整编译数据；不等时补 NUL 并追加文本缓冲区。没有任何将指针加 4 的剥头操作。裸 `"FC0A"` 路径在 `0x10017f52–0x10017f94` 先追加已读的四字节头，再追加余下文件内容，设置状态 4。长度 1 至 3 的文件按原始文本读取，状态为 0；长度至少 4 且不匹配三个已知头的文件在 `0x10017fad` 报错失败。

字节缓冲区到行集合的转换发生在 `objsys!0x10018000` 的 `0x100180bb–0x100180d9`：状态不是 4 或 5 时，函数以 FBase #137 取得缓冲区长度，调用 FBase #735，再清空临时缓冲区。FBase #735（`fbase!0x10011ca0–0x10011dcd`）用位于 FBase RVA `0x57484` 的分隔串搜索和切片；直接读取 `CLIENT/fbase.dll` 的 `.rdata` 可见该地址内容为 `0d 0a 00`，即严格的 CRLF。FBase #664 返回分隔符位置或 -1；每次匹配后，#735 将扫描位置推进两个字节，并通过 #705 构造片段、#724 加入行向量；找不到下一个分隔符时，无条件加入剩余尾段。

因此，该拆分规则只认 `\r\n`，不会单独按 `\n` 拆分，也没有额外剥离行尾 `\r` 的步骤。连续 CRLF 会产生空字符串行；尾随 CRLF 后的零长尾段也会被加入，因此保留末尾空行。FBase #705 对零长片段构造空字符串，#724 将空 C 字符串作为一个元素追加。空文件本身不会得到单空行结果：`0x10017b50` 对长度小于 1 的输入报错并失败。

状态 4/5 路径绕过 #735，字节缓冲区不会在此处转成行列表。状态 4 对应裸 FC0A，状态 5 对应 XY20 或 !CD1 解码后的 FC0A 编译数据。两者均完整保留 FC0A 头。短文本以及解码后不是 FC0A 的 XY20/!CD1 内容才进入严格 CRLF 拆分流程。以上是静态反汇编结论，未据此断言客户端运行时实际命中了哪种文件格式。

## URL、缓存与 miss 路径

`objsys!0x100190c0` 的 URL 分支先经 FBase #217（`0x10019193`）解析路径。非 URL 分支会直接通过 FBase #206（`FindFirstFileA`）查本地路径；URL 分支则在 `0x1001938c` 调 `objsys!0x10018c80` 查询全局缓存。#206 的实现位于 `fbase.annotated.asm:0x10008090–0x1000810d`。

`0x10018c80` 在缓存记录可用且目标文件存在时返回正值；调用点 `0x1001939a` 将 `EAX <= 0` 作为 miss，转入 `0x10019400`。miss 路径最多重试十轮（`0x100194d5–0x100194dd`、`0x1001957c–0x10019588`），每轮构造工作对象，并在 `0x100194b8` 调 `objsys!0x1001afb0`。该函数将以 `www.` 开头的地址补成 `http://`，执行窄字符到宽字符转换，再调用 COM 对象的间接方法（`0x1001b0a9–0x1001b181`）。这是静态证据支持的网络获取路径，不是单纯排队或立即失败。

工作对象的回调在 `objsys!0x1001ac20–0x1001ad45` 处理状态值 `200`，查询 `IID_IWinInetHttpInfo`，并用 `QueryInfo` 读取数值选项 `5` 和 `HTTP_QUERY_LAST_MODIFIED`（选项 `11`，带 SYSTEMTIME 标志）；相关失败分别记录 `QueryInterface IID_IWinInetHttpInfo err` 或 `QueryInfo HTTP_QUERY_LAST_MODIFIED err!`。这里的 `200` 是回调收到的状态参数，不能仅凭该值推断服务端 HTTP 响应状态码。COM 虚表调用的底层实现未包含在反汇编中，因此具体 COM 类、请求方法、完整回调状态映射及服务器响应语义仍未确定。

启动工作对象后，主线程在 `0x10019540–0x10019555` 每隔 20 ms 调 FBase #860 并检查对象偏移 `+0x6c` 的状态字段；状态不再为 `1` 时退出等待，随后以状态值 `3` 进入成功分支。若启动失败或最终状态不满足成功分支，会清理对象并重试，最多十轮；耗尽后进入日志/错误提示路径。成功分支继续校验本地缓存文件：在 `0x1001966a` 以 #206 检查文件，并在需要时用 FBase #915 处理它；之后调用 FBase #214。该导出实现（`fbase.annotated.asm:0x10008020–0x1000808f`）打开已有文件并调用 `SetFileTime`，用于设置文件时间，不是缓存索引更新。这些动作均未证明资源目录格式解析成功或目录有效。

对 `objsys!0x1001a0a0` 的实际调用，参数按压栈顺序为 `0, 0, outPath, inputPath`（`0x1001a0c8–0x1001a0da`）。`0x100190c0` 返回成功后，`0x1001a0a0` 才把输出路径交给 `objsys!0x10018000`；后者使用 FBase #209/#211 对本地文件执行 `CreateFileA` / `ReadFile`。所以 miss 分支确实尝试经 COM/WinInet 获取或促成缓存文件出现，但“工作对象报告成功”不等于“目录文件已成功读取”。若最终本地打开、读取或格式解析失败，`0x1001a0a0` 返回零，`0x1001a1a0` 跳过目录条目枚举，而更外层分派继续。

以上是静态反汇编结论，没有运行时观察；不据此声称实际服务器可达、下载成功或 `files_dir.dz` 属于某一种格式。主要地址范围：`objsys!0x100190c0`（`0x100190c0–0x1001977c`）、缓存查询 `0x10018c80`、worker 创建 `0x1001afb0`、HTTP 回调 `0x1001ac20`、调用者 `0x1001a0a0`。
