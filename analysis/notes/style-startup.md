# `style(kind=1521)` 启动路径

## 范围与证据边界

本记录聚焦 `style(kind=1521)` 定义节点的解析、登记及样式应用路径。原生证据来自 `CLIENT/objsys.dll` 对应的 `analysis/disassembly/objsys.annotated.asm` 静态反汇编。未运行原版客户端，不能据此声称已观察到该样式在游戏启动时执行。

## 已确认

- parser 在 `0x100110a5` 将 kind 减去 `0x5ea`，并以结果索引 `0x10011970` 的字节表，再通过 `0x10011938` 的地址表跳转。kind `1521` 对应索引 `7`，索引表第 7 项为 `2`，落到 `0x100110c1`；该通用名称解析分支继续汇入 `0x10011187`。
- `0x10011187–0x100111a7` 要求可解析名称；缺少名称时走错误分支，相关提示为 `style=need name`（`0x10011135`）。之后分配 8 字节节点并调用 `0x1000a050`（`0x100111a7–0x100111eb`）。成功时 `0x10011232–0x10011240` 将节点 opcode 写为 `0`，并通过 FBase #799 以 tag `4` 写入关联值。
- 执行器 `0x10065fa0` 按节点 `+4` 的 opcode 分派。opcode `0` 走 `0x1006604c–0x1006609c`：从节点 payload 取值，在执行上下文 `+0xb8` 建立/复用记录并调用 `0x1000a460`。这与类定义笔记所确认的登记路径一致；它只支持“定义登记”的静态描述，不证明样式体在登记时运行。
- `0x10066117–0x10066128` 处理 opcode `3` 的样式应用候选路径：取节点值并调用 `0x10065bc0`。后者遍历当前上下文及 `+0xa8` 父链，在各自 `+0xb8` 表中查询名称；命中后取记录关联字段，并在 `0x10065c0f` 起递归进入执行器。该调用链支持“查找后执行关联体”的数据流判断。
- `0x10066161` 附近另有字符串 `"style"` 以及 FBase #839 调用；由于该日志/事件调用的精确语义未确认，本记录不把它解释为样式应用的必要条件或结果。

## 关联脚本线索

主任务先前从 `SYSTEM.COD` 解码脚本中指出 `res$SYSTEM.COD:0x3170` 存在 `style drag` 定义。当前仓库未找到独立的 `SYSTEM.COD` 文件；该偏移线索来自主任务已有分析，不是本次对本地文件的重新验证。即使该定义存在，也还需要确认后续启动路径是否应用 `drag`、其定义体是否涉及游戏入口，以及各依赖资源是否齐备。

## Go 实现验证

Go 侧将 `style` 定义保存在当前对象的共享类定义表中但不执行定义体；`apply-style` 从当前对象沿 `Owner` 查找最近定义，并在当前对象上执行定义体。对应测试覆盖定义体延迟执行、父链查找、当前对象 receiver、同名覆盖、未登记/普通类拒绝，以及 Owner 环与递归深度限制。这些属于重建实现的行为选择与回归验证，不是对原版运行时的观察。

## 未知与边界

- FBase #799 的 tag `4`、#788 的值类型、`0x1000a050` 的完整高层语义，以及 `0x10065bc0` 命中记录字段的业务含义尚未完全恢复。
- opcode `3` 关联的具体 payload 是否在所有脚本形态下都是样式名，以及执行器递归执行的具体容器字段，仍需更完整的数据结构证据闭合。
- 没有证据证明 `SYSTEM.COD` 中的 `style drag` 已在启动时被应用，也没有证据证明该样式是进入游戏的充分条件。
- 本笔记不说明当前 Go 客户端已可进入游戏；启动成功还依赖完整脚本语义、对象工厂、资源加载、窗口/渲染与外部服务等链路的验证。
