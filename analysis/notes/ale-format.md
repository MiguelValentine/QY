# ALE/AEX 资源格式初步证据

本记录只描述本地 `CLIENT` 样本字节和既有静态反汇编能直接支持的内容；不执行原程序。`.ale` 不是单一可由扩展名确定的布局。

## 加载路径证据

- FBase 导出 `#63`（VA `0x1002a290`）按扩展名选择图片读取路径。`.ale` 在 `0x1002a5f9` 命中专用分支，`res$` 内置资源经 `#484` 装入流，再由 `0x1002a8a1` 调用 `#68`。`#68`（`0x10029f90`）检查 `ALE\0`，不匹配时转 `#69`（`0x100296b0`）检查 `AEX\0`。此前仅追踪 `#449`/OLE 通用图片分支而否定 `.ale` 读取能力的结论已被纠正；不能把该通用分支套到 TOOLTIPS.ALE。
- `analysis/disassembly/objsys.annotated.asm:2731` 标出 `FObjMap::AsyncLoadImgThread`，所在函数从 VA `0x10002de0` 开始，调用 FBase `#432`、`#446`，随后以资源路径/标识调用本模块 `0x10002d50`。这是异步图像对象加载路径的证据；所见代码没有给出 ALE 字段解析。
- FBase `#446` 的导出表地址为 RVA `0x23ba0`、首选 VA `0x10023ba0`（`analysis/evidence/fbase-headers.json`、`analysis/evidence/pe-inventory.json`；反汇编主体见 `analysis/disassembly/fbase.annotated.asm:54133`）。该函数初始化输入流（#190、#209），查询长度（#201），分配并锁定全局内存（`GlobalAlloc`、`GlobalLock`），再调用 `0x10022ed0`；后者在 `0x10023030` 比较 JPEG 标记 `FF D8 FF E0`，之后进入 `0x10040b10`。成功时 #446 调用 `#447`（VA `0x10023a60`），由 `CreateStreamOnHGlobal` 和 `OleLoadPicture` 创建 OLE 图片对象。因而 #446 是带 JPEG 路径的 OLE 图片加载辅助函数，不是 ALE magic 检查器或 ALE 帧读取器；它在 `AsyncLoadImgThread` 中被调用并不能证明它处理 `.ale`。
- FBase `#77`（VA `0x1002da40`）会调用 `#72`（VA `0x1002d450`），而 `#72` 调用 `0x1002d160` 处理行像素/命令缓冲区。这些函数体现图像像素转换路径，但目前这段反汇编没有展示 ALE 文件头检查或完整帧块读取。`#78`（VA `0x100276a0`）的 `ALE\0` 写入路径是序列化证据，不足以反推同一模块中存在何种磁盘读取函数。
- 对 `0x1002d160` 的参数和控制流进一步核对后，它是**生成**命令缓冲区的转换/编码函数，不是读取 ALE 命令的解码器。按该函数入口栈布局：`EDX` 是循环处理的字节项数；入口 `[ESP+8]` 是输入字节流（函数内 `EDI`，逐项步进1字节）；入口 `[ESP+4]` 是并行 `u16` 数据流（函数内 `ESI`，对应项步进2字节）；入口 `[ESP+12]` 是输出缓冲区（函数内 `EBP`）；`EBX` 是输出长度指针，函数先清零并随输出递增。该结论来自函数序言、`0x1002d184` 的输入指针装载，以及 `0x1002d178`、`0x1002d213`、`0x1002d216`、`0x1002d3e6` 等输出写入/计数指令。输入项数非正时输出长度为0并返回0。
- `0x1002d160` 的可见输出分支（地址均为 FBase VA）：
  - `0x1002d184..0x1002d217`：先统计连续 `< 8` 的字节项。若非零，推进对应 `u16` 流；计数达到255时按255项分段，逐段写 `FF 00` 并把输出长度加2，最后写余数/计数单字节。随后写当前字节值并继续分支。这里能确认输出字节形态，不能仅据此确定它在 ALE 文件中的语义名称。
  - `0x1002d219..0x1002d321`：当前输入字节 `> 0xF5` 时统计连续同类项；长段按127项分块，每块写 `7F`、复制254字节的 `u16` 数据，再写 `00`，输出长度每块增加 `0x100`；尾段写计数单字节并复制相应的 `2*n` 字节数据。短尾段只写计数和 `2*n` 字节数据。
  - `0x1002d328..0x1002d3be`：当函数当前栈帧 `[ESP+0x28]` 非零且当前字节为 `0x11` 时，统计连续 `0x11`。长段按31项分块写 `BF 00`，尾部写 `A0 | 余数`；其余按计数写一个 `A0 | n` 类命令字节。该分支读写位置按字节项推进。
  - `0x1002d3c0..0x1002d42e`：普通分支若还有多个项，且后续字节在 `0x08..0xF4`、不等于 `0x11`，则逐项输出三字节记录：`0xE0 | (当前字节 >> 3)` 加对应 `u16` 的两个原始字节；最后一项使用 `0xC0 | (当前字节 >> 3)` 加两个原始字节。否则直接输出最后项的 `C0` 类三字节记录。
- `#72` 的调用点 `0x1002d5c4..0x1002d5d3` 按行/矩形坐标计算两路输入地址，再调用上述函数。写流实参证实了行记录边界：`0x1002d5d6` 保存 #160 的 `EAX` 返回值到局部变量，`0x1002d610..0x1002d61b` 将其按2字节写出；`0x1002d620..0x1002d633` 取 #160 更新的输出长度并按2字节写出；`0x1002d638..0x1002d645` 再写相同长度的命令字节。故每条有数据的行记录为 `u16(#160返回值原样保留)`、`u16(编码字节长度)`、对应长度的原始命令数据。若之前累积了空行，`0x1002d5ef..0x1002d600` 会在该行记录前另写一个负的 `i16` 跳行数。`0x1002d6ea..0x1002d6f2` 在帧载荷起始处另写2字节维度局部值；其字段语义以原始值保存，不在这里命名。
- `bullet.ale` 两帧载荷偏移 `0x24` 起均可按上述布局精确闭合：2字节前缀后各有7条行记录，`(返回值, 数据长度)` 依次为 `(2,23),(1,22),(3,22),(3,22),(3,22),(1,22),(1,22)`。`maxpos.ale` 解析为8行，字段依次为 `(1,22),(3,24),(3,24),(3,24),(3,24),(1,25),(1,25),(2,26)`；`man_01.ale` 解析为28行，前16行长度126，后续长度依次为124至102、每行减2，行记录也全部精确闭合。帧前缀原值在这三个样本中分别为7、8、28。`#72` 的写流结构与这些帧载荷相符；这仍不证明 `0x1002d160` 输入就是文件帧载荷，也不恢复像素命令语义。编码命令中的普通分支确实含“1字节控制头 + 原样2字节数据”，但不能据此将它们命名为 alpha/RGB565。
- `analysis/disassembly/objsys.annotated.asm:61440` 附近，VA `0x1002f350` 报 `"Get Palette obj is err!"`，VA `0x1002f620` 的加载逻辑报 `"palette file format err!"`。这些是调色板对象/调色板格式路径，不应误认为 ALE 解码器。

## 已恢复的 ALE v3 序列化布局

FBase 导出 `#78`（VA `0x100276a0`，`analysis/disassembly/fbase.annotated.asm:59400` 附近）写文件时明确写入 `ALE\0`，调用 `#219`（VA `0x10007ea0`，封装 `WriteFile`）：

1. `ALE\0` 4字节。
2. 版本 `u16`。
3. 所有帧块总长度 `u32`。
4. 帧块数量 `u16`。
5. 版本1额外写1024字节，版本2额外写4字节；版本3没有这段版本专属数据。
6. 按数量逐块写出每个帧块；块指针首个 `u32` 是含自身长度字段的块总长。
7. 写 `END\0` 4字节。

该顺序与版本3样本精确闭合：

| 文件 | 声明块总长 | 块数与块长 | 闭合计算 |
|---|---:|---|---|
| `bullet.ale` | 418 | 2 × 209 | `12 + 418 + 4 = 434` |
| `maxpos.ale` | 252 | 1 × 252 | `12 + 252 + 4 = 268` |
| `man_01.ale` | 3510 | 1 × 3510 | `12 + 3510 + 4 = 3526` |

每个v3块在长度字段后的前20字节，样本可解读为 `u32保留值、u32宽、u32高、i32偏移X、i32偏移Y`。例如 `bullet.ale` 的单块元数据为 `0,7,7,0,0`；`maxpos.ale` 为 `0,8,8,-3,-2`；`man_01.ale` 为 `0,62,28,0,0`。因此v3块余下部分是图像/绘制载荷，但这段静态证据没有确定其逐命令语义、像素格式或压缩算法。

版本1的 `cannon.ale` 确认头版本为1；虽`#78`显示该版本会写1024字节额外数据，尚未用该代码路径与该磁盘样本完全对齐字段，故不把这1024字节臆定为某种颜色表。`AEX` 也未在这段 `ALE\0` 写入器中解释。

## 已恢复的行命令读取

`internal/ale.DecodeRow` 按上述 `0x1002d160` 编码分支逆读行命令，输出每列的 alpha 代表值和可恢复的原始 `u16`。它支持 `<8` 透明段及 `FF 00` 扩展、`A0..BF` 的 `0x11` 段、`E0..FE` 延续与 `C0..DF` 结束的量化 alpha 记录，以及 `1..7F` 的高 alpha 原始 `u16` 段（含长段分块）。颜色由独立的 `Color565` 转换；格式4及RGB565的补充证据见 [ale-colors.md](ale-colors.md)，前文仅描述初次分析当时未确定的部分。

行编码会省略行尾连续的 `<8` 输入项；解码时将剩余宽度补成 alpha 代表值0，并以 `AlphaExact=false` 标记它并非原 alpha 精确值。普通量化记录只保留 `alpha >> 3`，高 alpha 段只确认输入 alpha 大于 `0xF5`，因此这些值也标记为非精确；`0x11` 特殊段是当前可证实的精确 alpha。`HasRawU16` 仅表示该命令携带并恢复了原始两字节数据，不赋予其 RGB565 或其他颜色语义。

这一行解码器是已知编码函数的逆过程，不构成完整图像渲染器。结合颜色转换后，`Frame.Preview` 可以生成受支持帧的PNG预览；特殊绘制命令、原生混色与版本1仍未恢复。后续已确认 `#68/#69` 的 ALE/AEX 签名分派及 AEX 容器、解密和 GIF 平面，帧转换与绘制仍须逐项核对。

### 原生编码器交叉验证

`analysis/tools/oracle_ale_rows.py` 使用 Unicorn 2.1.4 与 pefile 2024.8.26，将 `CLIENT/fbase.dll` 映射到其首选基址并从 VA `0x1002d160` 调用函数；DLL SHA-256 为 `98bb2c6ef0c67b719aafda61f7799f6c80a9b13206a4e2e3c200b89722ecedaf`。调用约定取自函数序言和读写指令：`EDX` 为输入项数、`EBX` 指向输出长度，栈参数依次为原始 `u16` 流、alpha 流、输出缓冲区及特殊 alpha 模式。仿真不运行 DLL 初始化或其他导出函数。

证据文件 `analysis/evidence/ale-row-oracle.json` 保存七组输入及原生返回值、编码长度和完整输出字节；`TestDecodeRowsNativeOracle` 将这些输出交给 Go 解码器并逐项比对 alpha 代表值和 `u16`。样本覆盖两次 `FF 00` 扩展、恰好127项及跨127分块后接下一组、恰好31项及跨31分块、普通量化 alpha 终止，以及透明行尾省略。仿真确认 `0x11` 特殊段不携带 `u16`，尽管输入 `u16` 指针会同步前进。该验证证明这些构造输入下编码输出与解码器一致，不扩展为颜色格式或其他 ALE 版本的证据。

## Go 解析器验证

`internal/ale.Parse` 接受 ALE v3 容器，校验头、帧数、长度边界、尺寸上限、`END\0` 和文件尾；帧载荷以原始切片返回。测试逐行解码真实样本，并通过上述 Unicorn 原生输出对照。独立的 `ParseAEX` 解密并解码两个 GIF 平面，原样保留记录；非零附加字典块明确拒绝。它不把 GIF 原图冒充原生裁剪、透明度处理后的帧。
