# FC0A 标记值与字段链接

## 范围与结论

本文只记录对 `CLIENT/objsys.dll` 现有静态反汇编及真实 `index.fcc` 中 `tmp.cod` 的核对结果。未启动原程序、未连接资源中出现的服务地址。

磁盘上的每个普通标记至少是 `uint16 kind + uint32 value`。这里的 `value` 不能一概解释成文件偏移、字符串池索引或括号配对索引。对象系统在读取时按 kind 把 DWORD 放入不同的联合字段；kind 4 还会将相同布局扩展为数据长度和数据指针。

## 读取器证据

`objsys:0x1000eb20` 是标记读取路径。它先经 `FBase!#136`（`0x1009d570`）读取 2 字节 kind，写入新标记对象偏移 `+0`，并将偏移 `+4` 初始化为 `1`（`0x1000eb43–0x1000eb7b`）。随后用 `kind - 2` 索引 `0x1000ed30` 的五项跳转表：

| kind | 分支 | 读取/存放证据 | 可确认的含义 |
|---:|---|---|---|
| 2 | `0x1000eb93` | `FBase!#136` 从输入读 4 字节到对象 `+12`；`FBase!#134` 前移 4 字节；对象 `+8` 置 0 | 内联 DWORD，未发现将其当作流偏移或池下标的证据 |
| 3 | `0x1000ece8` | 读 4 字节到对象 `+8`，对象 `+12` 置 0 | 内联 DWORD；结合样本与字符串池哈希函数，作为池字符串哈希有强证据 |
| 4 | `0x1000ebbb` | 读 DWORD 到对象 `+12`；小块直接取数据，大块可能经 `FBase!#882` 解压，数据指针保存在 `+8` | 长度加数据指针的 blob 标记；`0x1000e6d0–0x1000e6f6` 在释放 kind 4 对象时释放 `+8` |
| 5 | `0x1000ed10` | 读取 4 字节到对象 `+12`，对象 `+8` 置 0 | 内联 DWORD；与 kind 2 采用相同联合字段位置，但具体语言类型/语义未恢复 |
| 6 | `0x1000ece8` | 与 kind 3 共用分支，读 4 字节到对象 `+8`，对象 `+12` 置 0 | 内联 DWORD；静态字段布局不同于 kind 2/5。样本显示可能是符号哈希，池缺失不能据此补名 |

`0x1000ed30` 的五项（按 little-endian DWORD）分别指向 `0x1000eb93`、`0x1000ece8`、`0x1000ebbb`、`0x1000ed10`、`0x1000ece8`，由此对应 kind 2–6。

`FBase!#136`、`FBase!#134` 的外部函数主体不在该 DLL 反汇编中；读取宽度可由调用前压入的 `2` 或 `4` 和后续对象写入位置交叉确认。

## 真实样本交叉核对

`CLIENT/index.fcc` 解出的 `tmp.cod` 与静态证据记录中的 `analysis/decoded/index/tmp.cod` 同一成员。文件头显示标记区从 `0x14` 开始。当前 Go 标记转储（仅作为离线格式核对，不代表执行语义）给出：

| 文件偏移 | kind | value | 交叉核对 |
|---:|---:|---:|---|
| `0x38` | 6 | `0xdc331502` | 字符串池没有对应候选；显示为未解析符号哈希，不应伪造名称 |
| `0x3e` | 3 | `0x58fceeb2` | 与池中 `FW@kele8_Ver103` 匹配；算法为 `FBase!#858` 对应的 `StringTableHash` |
| `0x86` | 2 | `0x86` | 被读取为内联整数 `134`，不是指向自身的文件偏移 |
| `0xb0` | 6 | `0x2dc4903a` | 池中存在 `__PATH__` 候选；这是候选匹配，不足以证明所有 kind 6 都是池字符串 |
| `0x50` | 101 | `0x0a` | 静态 KindName 表将 kind 101 命名为 `(` |
| `0x5c` | 980 | `0x62` | 静态 KindName 表将 kind 980 命名为 `)` |
| `0x62` | 1230 | `0x7b` | 静态 KindName 表将 kind 1230 命名为 `;` |

括号标记的 value 是固定伴随数值，而非能指向本文件配对标记的偏移：样本中开括号标记 `0x50` 的 value 为 `10`，闭括号标记 `0x5c` 的 value 为 `98`；读取器仅把它们作为标记联合字段中的 DWORD 读入，没有在此处建立反向/配对链接。当前静态证据不足以确定这些伴随数值是否是词法类别码、枚举值或其它编译器内部元数据，因此不应解释成字符 ASCII、源码位置或括号配对表。

运算符也显示类似的固定附带值，例如 `=`（kind 200）value `20`、`.`（kind 940）value `94`、`+`（kind 801）value `80`。KindName 表提供的是 kind 到可读名称的映射，不能因此推导 value 的完整语义。

## 边界与未知项

- kind 2 的样本和读取布局支持“内联整数”；其他文件中它是否承载浮点位模式或别的数值子类型，尚需读取消费端才能确定。
- kind 3 在样本中匹配字符串池哈希；全局名称/字面量的完整区分规则尚未恢复。
- kind 5 虽与 kind 2 一样写入 `+12`，但没有足够的真实消费路径证据给它命名为布尔值、浮点数或其它类型。
- kind 6 与 kind 3 共用 `+8` 布局，样本内既有池命中也有未命中；未命中通常显示为符号哈希候选，但“kind 6 一定是全局符号”的命题尚未由完整解释器调用链证明。
- 当前结论只覆盖读取及对象字段布局，未恢复表达式求值、运算符优先级、跳转目标或完整 token 配对机制。

## 表达式与语句结束标记

对 `objsys:0x1000ffa0`（编译/语法处理入口）及其调用的 `0x1000f9a0`（表达式解析）作静态核对后，必须区分“表达式停止”和“语句结束”：

- `0x1000f9a0` 前瞻读取下一个标记，并按标记 kind 分支构造表达式；函数内能看到 `;`（kind 1230，立即数 `0x4ce`）、`)`（kind 980，立即数 `0x3d4`）等停止上下文，但在该函数地址范围内未发现对换行 kind 1900（`0x76c`）的显式比较。因此不能仅凭此函数断言换行一定终止一般表达式语句。
- `0x1000f200` 是按 kind 精确匹配下一个 token 的帮助函数。`if` 分支在 `0x100109c0–0x100109e1` 解析表达式后要求 `)`（错误字符串 `if need ')'`）；`for` 分支在 `0x10010b40–0x10010b61` 解析初始化表达式后要求 `;`（错误字符串 `for need ';'`），继而在 `0x10010b80–0x10010ba1` 要求第二个 `;`。这证明特定语法位置要求明确分隔符，不代表所有普通表达式语句都必须有分号。
- 原生入口将 `}`（kind 1101，`0x44d`）作为块结构标记处理，和普通表达式运算符不同。真实 `CLIENT/index.fcc` 的 `tmp.cod` 在偏移 `0x4550–0x4568` 有完整的 `__PATH__ + "sound/mousefire.adm"` 调用，偏移 `0x456e` 是换行，随后 `0x4574` 是 `}`，调用后没有分号。该资源支持“块结束前可省略最后一条普通表达式语句的分号”的实现推断，但未由原 EXE 动态验证。Go 解析器对该样本的接受只是回归结果，不能作为原生语义的独立证据。

### 实现建议与未知

应允许普通表达式语句在 `}` 前结束而不要求 `;`。不要把它推广到 `for` 的两个分隔位置或其它由原生解析器明确要求标点的语法。

这个样本同时含“换行”和紧随的 `}`，无法区分是换行结束前一条语句，还是块闭合本身结束最后一条语句。`0x1000f9a0` 中也没有找到对 kind 1900 的直接处理证据；因此当前不能确认孤立换行是否可终止语句，建议将其标记为待更多真实样本验证，而不要把全局丢弃换行解释成已恢复了原生规则。换行在两个可继续表达式的行之间是否作为空白、以及其它语句末尾的隐式终止条件，同样未由本次证据确定。

### 冒号与循环控制标记

- `0x100112f6–0x10011314` 的 `class` 分支在取得类名后以 `0x1000f200` 精确要求 kind `1220`（`:`，立即数 `0x4c4`），随后读取基类名。故此处可确认冒号分隔类名与基类名；这不能单独证明其它语法位置中冒号的含义。样本 `analysis/decoded/act/fight/ani/tmp.cod` 的 `0x12b0` 也是 kind `1220`，但其消费端尚未定位，不能据此将普通语句写成构造、继承或方法绑定。
- 语句入口在 `0x10010ab2` 对 kind `0x5de–0x5e8` 使用跳转表；kind `1512`（`break`，`0x5e8`）映射到 `0x10010ac7`。该分支检查当前解析上下文的循环标志，不满足时走错误路径，满足时设置节点标志并返回主循环；此分支没有调用 `0x1000f200` 要求 `;`。因此当前证据支持 `break` 不要求显式分号，而不是只因某个样本省略分号。
- 相邻分发表项 `0x10010aeb` 对应 kind `1503`（`continue`，`0x5df`），采用同类上下文检查并设置另一控制标志，也没有分号匹配调用。`analysis/decoded/lobby/shop/shoper/tmp.cod` 中实际观察到的是 kind `1512`（`break`，`0x5e8`），位于偏移 `0x6a68`；其后为换行 kind `1900` 和 `}`，没有分号。
