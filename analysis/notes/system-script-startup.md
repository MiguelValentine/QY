# SYSTEM 脚本启动路径静态证据

## 范围与证据

本文核对 `objsys.dll` 中 `0x10060080` 的系统初始化路径，重点检查脚本读取、编译和执行顺序，以及 `SYSTEM.FCC` 是否也在该入口被加载。证据来自 `analysis/disassembly/objsys.annotated.asm`、REA 资源清单 `analysis/evidence/objsys-resources.json` 和 DLL 字符串/PE 清单；没有运行原版客户端。地址是装载基址 `0x10000000` 下的 VA。

## 初始化顺序

- `0x10060080` 初始化对象字段后，调用 `0x1000f110` 建立临时字符串/路径对象（`0x100600e2–0x100600f2`）。随后准备文件名 `SYSTEM.COD`、路径提示 `E:/fcbox2/ObjSys/res/system.cod` 以及其他路径参数，并调用 `0x10011d70`（`0x100600fc–0x1006012d`）。因此此入口明确以 `SYSTEM.COD` 为读取对象；反汇编中的绝对路径是常量/回退路径提示，不能单凭它断定最终从哪个介质读取。
- `0x10011d70` 调 FBase #222 检查/解析传入资源名及路径（`0x10011d91–0x10011dd0`）。成功后，如果一个路径参数为空，就构造 `res://%s`；否则使用提供的路径值，然后调用 `0x10011c30` 处理该输入（`0x10011e0a–0x10011e74`）。失败则返回空并记录路径相关错误（`0x10011d2b–0x10011d64`）。`0x10011c30` 将输入数据交给 `0x10011990`，并把长度/选项等参数转发；这支持它是数据读取/装载路径，但仅凭这些调用不能断言所有资源名都一定命中 PE 资源表。
- `0x10060080` 检查 `0x10011d70` 返回值；成功时初始化若干 parser/context 对象，再调用 `0x1000ffa0`（`0x10060146–0x10060180`）。只有当 `0x1000ffa0` 返回成功，才以该返回记录为首个参数调用 `0x10065fa0`（`0x10060180–0x100601a4`）。所以可见顺序是：请求 `SYSTEM.COD` 数据 → 编译/解析入口 `0x1000ffa0` → 执行入口 `0x10065fa0`。读取、编译任一步失败都有错误分支；静态顺序不等于运行时必定成功。
- `0x1000ffa0` 的函数体包含输入对象解析、节点构造和语法错误处理；`0x10065fa0` 则从传入节点的 `+4` 字段分派执行语句。以上“编译”和“执行”是对两段功能与调用关系的描述，不表示完整恢复了虚拟机语义。

## 执行结果与初始化调用者

- `0x10060080` 在 `0x100601a4` 调用 `0x10065fa0` 后直接进入资源清理流程（`0x100601a9` 起），没有测试执行器的 EAX，也没有把执行器结果转换为返回状态；函数随后在 `0x100601d5` 返回。读取或编译失败分支会记录相应错误并清理，但不能与执行器返回值处理混为一谈。
- 桌面初始化调用者 `0x10062c20` 在 `0x10063550` 调用 `0x10060080` 后继续清理并收尾，且在 `0x10063591` 将 EAX 设为 1 后返回；调用点没有检查 `0x10060080` 的执行结果。另一调用者 `0x10063aa0` 在 `0x10063b1c` 调用后从 `0x10063b21` 继续初始化，未见返回值检查；其上层 `0x100643ae` 调用后也继续后续初始化。
- 因此，这些已检查的静态路径没有把系统脚本执行状态作为错误返回传播给桌面初始化调用者。错误仍可能通过执行上下文、全局状态或已发生的副作用影响后续行为；静态调用流本身不能证明客户端必然成功完成初始化。
- 本节只闭合 `SYSTEM.COD` 执行及其桌面初始化调用者的返回值处理，没有闭合原生入口脚本 `index` 随后的具体调用位置。因此不能仅凭调用者忽略状态就断言客户端必然进入游戏，或 Go 实现可以忽略任意系统脚本错误。

## SYSTEM.FCC 与 PE 资源表

- `analysis/evidence/objsys-resources.json`（Evidence `ev_39c4876f1d896585d3fc56f35416264c4e08b1475ab3ba32789f18878133b5cd`）记录 `objsys.dll` 的两个同级 `FCC` 类型、language 2052 资源：index 2 `SYSTEM.COD`，payload 文件偏移 `869488`、大小 `4936` 字节；index 3 `SYSTEM.FCC`，偏移 `874424`、大小 `14960` 字节。资源清单证明二者都嵌在 DLL 中，不证明它们会在同一启动入口被读取。
- 在 `0x10060080` 的可见路径中，传给 `0x10011d70` 的显式名称只有 `SYSTEM.COD`。该函数的可见后续流程编译并执行这次返回的数据；没有第二次传入 `SYSTEM.FCC` 的读取调用。因此当前证据不支持“此入口顺序加载 SYSTEM.COD 后再加载 SYSTEM.FCC”。
- 这也不是“整个进程绝不读取 SYSTEM.FCC”的证明：它可能由其他函数、资源查找回调、`SYSTEM.COD` 引用的指令或其他初始化入口间接读取。对本函数文本和相邻调用链而言，未看到显式 `SYSTEM.FCC` 请求；无法据此排除间接/运行时访问。
- PE 资源 type/name 的共同出现仅证明资源表登记。资源名为 `SYSTEM.FCC` 并不能推出它是被 `SYSTEM.COD` include，也不能推出两个 payload 被合并、共享解析上下文或先后执行。

## 宏预处理与资源关联边界

- `objsys` 中存在独立的宏/预处理指令处理代码：可见错误/处理分支包含 `#define`（`0x1000d439`）、`#ifdef` / `#else`（`0x1000d53c–0x1000d54d`）、`#endif`（`0x1000d607`）、`#push all macro`（`0x1000d927`）、`#pop all macro`（`0x1000da59`），另有 `#include` 错误路径和 import 处理（`0x1000da15`、`0x1000d99e`）。这确认引擎实现这些预处理指令及宏状态保存/恢复路径。
- 这些指令处理代码位于同一 DLL 的 parser/preprocessor 相关区域，但静态证据尚未闭合 `0x10060080 → 0x1000ffa0` 与每个宏处理分支的完整调用链，也未证明 `SYSTEM.COD` 编译时读取/修改的宏表是否与 `SYSTEM.FCC` 相关解析共享。共享宏机制是可见的引擎能力，不能直接等同于这两份资源在启动时共享状态。
- DLL 资源加载路径另有 PE API 证据：例如 `0x10063384` 起调用 `FindResourceA`、`LoadResource`、`LockResource` 加载名为 `GB2BIG5`、`BIG52GB` 的 `BDATA` 资源。该路径证明模块会从 PE 资源表取数据，但目前未发现该函数在此处查找 `SYSTEM.COD` 或 `SYSTEM.FCC`；资源表中二者的存在不能反向证明走了这条专用加载路径。

## 结论

已确认的启动链为 `0x10060080` 显式请求 `SYSTEM.COD`，将读取结果送入 `0x1000ffa0`，成功后将解析结果送入 `0x10065fa0` 执行；但执行器状态未由此函数返回，也未被已检查的桌面初始化调用者直接检查。DLL 的 PE 资源表同时包含 `FCC/SYSTEM.COD` 与 `FCC/SYSTEM.FCC`，但在该初始化入口可见的名称请求只有 `SYSTEM.COD`，没有直接加载 `SYSTEM.FCC` 的证据。引擎有宏定义、条件编译、include/import 和 push/pop 宏路径；两份资源之间的引用关系、宏表共享关系，以及 `SYSTEM.FCC` 是否由其他入口或间接路径读取，均未闭环。原生 `index` 后续调用点及“必然进入游戏”的结论不在本笔记已闭合的证据范围内。
